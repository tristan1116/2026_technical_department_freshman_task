# 第一章 先搞懂：网页背后发生了什么

## 1.1 你每天都在用，只是没注意

场景：你在淘宝搜索框输入"耳机"，点搜索，屏幕上出现一列商品。

**这不到 1 秒的时间里，发生了三件事**：

```
① 浏览器把你的操作变成一条"请求"，通过网络发出去
        ↓
② 淘宝的服务器收到请求 → 去数据库里找所有耳机 → 打包成"响应"发回来
        ↓
③ 浏览器收到数据 → 画成你看到的商品列表
```

画成图：

```
┌──────────┐   ① 请求："给我所有耳机"     ┌────────────┐   ③ 查数据   ┌──────────┐
│  浏览器   │ ─────────────────────────▶ │   服务器    │ ──────────▶ │  数据库   │
│ (前端)    │                            │  (后端)     │ ◀────────── │  MySQL   │
│          │ ◀───────────────────────── │            │   ④ 返回结果 │          │
└──────────┘   ⑥ 画成界面   ⑤ 响应：数据  └────────────┘              └──────────┘
```

**关键认知**：浏览器只负责"画界面"和"发请求"，**真正干活的是服务器**。

> 我们写的"后端"，就是图里中间那个"服务器"。

## 1.2 服务器是什么？——一个"永远在等"的程序

对比一下两种程序：

**普通程序**（比如计算器）：运行 → 算出结果 → 结束退出。

**服务器程序**：启动后**不结束**，它挂在那里等：

```
启动 → 挂起等待 → 来了一个请求！→ 处理 → 返回结果 → 继续挂起等待 → ...
                 ↑                                      │
                 └──────────────────────────────────────┘
                            （永远循环，直到你手动关掉它）
```

这个"永远在等"的动作，在代码里就是最后这一行：

```go
// main.go 的最后一行
r.Run(":8080")
```

`Run` 会**一直阻塞在那里**，不会往下执行，也不会结束 —— 这就是为什么你双击 `lostfound.exe` 之后，
那个黑窗口一直开着不关。**它在等请求。**

`:8080` 是"端口号"，你可以理解成**门牌号**：
一台电脑上可以同时跑很多个服务，端口号用来区分"这个请求是找哪个服务的"。
我们占用了 8080 号门。

## 1.3 请求长什么样？——解剖一条 HTTP 请求

浏览器发给服务器的东西，原文长这样（这是真实的一条）：

```http
POST /api/items HTTP/1.1              ← 第 1 行：方法 + 路径
Host: localhost:8080                   ┐
Authorization: Bearer eyJhbGciOiJ...   │ 请求头（Header）
Content-Type: application/json         ┘   = 附加信息，像信封上写的备注
                                       ← 空行（必须有，用来分隔头和内容）
{"type":"lost","title":"校园卡"}        ← 请求体（Body）= 真正要传的数据
```

拆开看，一条请求只有 **4 个部分**：

| 部分 | 是什么 | 类比 |
|---|---|---|
| **方法** | 你要办什么事（见下表） | 去银行取号时选的业务类型 |
| **路径** | 你要找哪个功能 | 窗口号 |
| **请求头** | 附加信息（比如"我是谁"） | 信封上写的寄件人、备注 |
| **请求体** | 真正要传的数据 | 信封里的信纸 |

### 五个方法（记住这 5 个就够用）

| 方法 | 中文意思 | 我们项目里用来干嘛 |
|---|---|---|
| `GET` | **我要拿数据** | 查列表、查详情 |
| `POST` | **我要新建** | 注册、登录、发布帖子 |
| `PUT` | **我要整体修改** | 编辑帖子 |
| `PATCH` | **我要改一小部分** | 只改状态 |
| `DELETE` | **我要删除** | 删帖子 |

> 为什么要分这么细？因为"查"和"删"是完全不同的事，
> 分开之后，光看请求的第一行就知道对方想干嘛，不用看内容。

## 1.4 响应长什么样？——解剖一条 HTTP 响应

服务器回给浏览器的东西：

```http
HTTP/1.1 200 OK                        ← 第 1 行：状态码
Content-Type: application/json          ← 响应头
                                       ← 空行
{"code":0,"message":"ok","data":{...}}  ← 响应体：真正的数据
```

**状态码**是"这次请求的结果"，我们项目里只会出现这 5 个：

| 状态码 | 意思 | 什么时候出现 |
|---|---|---|
| `200` | 成功 | 一切正常 |
| `400` | 你传的参数有问题 | 比如密码只填了 3 位 |
| `401` | 你没登录（或登录过期了） | 没带 token 就想看联系方式 |
| `403` | 你登录了，但没权限 | 想改别人发的帖子 |
| `404` | 你要找的东西不存在 | 查一个不存在的帖子 ID |
| `500` | 服务器自己出错了 | 代码有 bug（我们要尽量避免） |

> **400 / 401 / 403 / 404 的区别很重要**，第六章还会细讲：
> 401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能动这个"。

## 1.5 JSON 是什么？——双方约定好的"数据写法"

服务器和浏览器之间传数据，得用一种**双方都认识**的格式，我们用 JSON。

它长得像这样：

```json
{
  "code": 0,
  "message": "发布成功",
  "data": {
    "id": 4,
    "title": "校园卡",
    "status": "searching"
  }
}
```

**规则只有几条**：

| 规则 | 例子 |
|---|---|
| 用 `{}` 包一个"对象" | `{"name":"小明"}` |
| 键（key）**必须**用双引号 | `"name"` ✅ ｜ `name` ❌ |
| 值可以是字符串/数字/真假/null | `"小明"` / `18` / `true` / `null` |
| 用 `[]` 包一个"数组"（列表） | `[{"id":1},{"id":2}]` |
| 多项之间用逗号隔开 | `{"a":1,"b":2}` |

> **注意**：JSON 里**不能写注释**，也不能有多余的逗号（最后一项后面加逗号会报错）。
> 这是新手最常犯的两个错。

## 1.6 我们的项目：一句话说清

**"校园失物招领系统"就是一个存失物招领信息的服务**，规则是：

- **谁都能看** —— 列表、详情不用登录
- **登录了才能** —— 发帖、看联系方式、管理自己的帖子
- **自己的帖子才能** —— 改、删、改状态

对外提供 **12 个接口**（接口 = 一种"对话方式"）：

| 分类 | 接口 | 要登录吗 |
|---|---|---|
| 认证 | 注册、登录 | 不用 |
| 认证 | 获取当前用户、退出登录 | ✅ 要 |
| 物品 | 列表（搜索/筛选/分页）、详情 | 不用 |
| 物品 | 发布 | ✅ 要 |
| 物品 | 我的发布 | ✅ 要 |
| 物品 | 查看联系方式 | ✅ 要 |
| 物品 | 编辑、改状态、删除 | ✅ 要 + **必须是本人** |

# 第二章 我们用的三个工具

我们的项目没有"从零造轮子"，而是用了三个成熟的工具。先用大白话认识它们。

## 2.1 Gin —— 管"路由"的

**问题**：服务器收到请求后，怎么知道该交给哪段代码处理？

**答案**：查一张"对照表"，这张表就叫**路由表**。

```go
r.GET("/ping", func(c *gin.Context) {
    c.JSON(200, gin.H{"message": "pong"})
})
```

这一行意思是：**"有人用 GET 访问 `/ping` 时，执行后面这个函数"**。

但你可能有一堆疑问：`r` 是什么？`.GET` 是什么？后面那些参数是怎么定的？为什么能这么写？

**下面全部拆开讲。**

---

### 2.1.1 Gin 提供的三大类型

| 类型 | 是什么 | 怎么得到它 |
|---|---|---|
| `gin.Engine` | **引擎**：整个服务器的大脑 | `gin.Default()` |
| `gin.RouterGroup` | **路由分组**：一组路由的集合 | `引擎.Group("/api")` |
| `gin.Context` | **上下文**：一次请求的全部信息 | Gin 自动创建，作为参数传给你的处理函数 |

对应到我们的代码：

```go
r := gin.Default()            // r     是 *gin.Engine
api := r.Group("/api")        // api   是 *gin.RouterGroup
items := api.Group("/items")  // items 也是 *gin.RouterGroup（分组可以嵌套）

r.GET("/ping", func(c *gin.Context) {   // c 是 *gin.Context
    c.JSON(200, gin.H{"message": "pong"})
})
```

### 2.1.2 Gin 提供的两个"快捷类型"

| 类型 | 完整写法 | 用途 |
|---|---|---|
| `gin.H` | `map[string]any` | 快速拼 JSON 对象：`gin.H{"message": "pong"}` |
| `gin.HandlerFunc` | `func(*gin.Context)` | **处理函数的"标准形状"**（重点，见 2.1.4） |

### 2.1.3 Gin 提供的全部方法（我们项目用到的）

**A. 引擎/分组上的方法 —— 用来注册路由**

| 方法 | Gin 源码里的完整签名 | 用途 |
|---|---|---|
| `.GET(path, handlers...)` | `GET(relativePath string, handlers ...HandlerFunc) IRoutes` | 注册 GET 路由 |
| `.POST(path, handlers...)` | 同上 | 注册 POST 路由 |
| `.PUT(...)` / `.PATCH(...)` / `.DELETE(...)` | 同上 | 注册其他方法 |
| `.Group(path)` | `Group(relativePath string, handlers ...HandlerFunc) *RouterGroup` | 建子分组，**返回新分组对象** |
| `.Use(handlers...)` | `Use(middleware ...HandlerFunc) IRoutes` | 挂全局中间件 |
| `.Run(addr)` | `Run(addr ...string) error` | 启动服务、监听端口 |

**B. Context 上的方法 —— 在处理函数里用**

| 方法 | 用途 | 我们项目里用在哪 |
|---|---|---|
| `c.JSON(code, obj)` | 返回 JSON 响应 | `utils/response.go` |
| `c.ShouldBindJSON(&req)` | 解析请求体 + 按 `binding` 标签校验 | 所有 POST/PUT/PATCH 接口 |
| `c.Query("k")` | 取 URL 问号后的参数 | 列表的 keyword / type 等 |
| `c.DefaultQuery("k", "默认")` | 取 URL 参数，没有就用默认值 | 分页、状态筛选 |
| `c.Param("id")` | 取路径参数（`:id` 那段） | 详情、编辑、删除 |
| `c.GetHeader("k")` | 取请求头 | 中间件取 `Authorization` |
| `c.Set(k, v)` | 往上下文里**存**东西 | 中间件存 `user_id` |
| `c.GetUint(k)` | 从上下文里**取**（转成 uint） | controller 取 `user_id` |
| `c.Abort()` | **中断**：后面的处理函数不执行 | 中间件验不过时 |
| `c.Next()` | **放行**：交给下一个处理函数 | 中间件验过后 |

---

### 2.1.4 ★ 逐参数拆解：`items.GET("", controller.ListItems)`

先看 Gin 源码里 `GET` 方法的**完整签名**：

```go
func (group *RouterGroup) GET(relativePath string, handlers ...HandlerFunc) IRoutes
```

拆成三部分，逐个对应我们的代码：

| 签名里的部分 | 类型 | 我们传的 | 含义 |
|---|---|---|---|
| `group` | `*RouterGroup` | `items` | **接收者**：在哪个分组上注册（写在函数名**前面**） |
| `relativePath` | `string` | `""` | **相对路径**（相对于分组前缀） |
| `handlers` | `...HandlerFunc` | `controller.ListItems` | **处理函数**，可以传多个 |

#### ① `relativePath` 为什么是空字符串 `""`？

因为它是**相对路径**，不是完整路径。

```go
items := api.Group("/items")   // 分组前缀 = /api + /items = /api/items

items.GET("", ...)      // "" + 前缀    = /api/items
items.GET("/my", ...)   // "/my" + 前缀 = /api/items/my
items.GET("/:id", ...)  // "/:id" + 前缀 = /api/items/:id
```

> `""` 的意思是"**不加任何后缀，就用分组前缀本身**"。

#### ② `...HandlerFunc` 里的 `...` 是什么？

`...` 叫**变长参数**（variadic）：**这个位置可以传 0 个、1 个、或多个**。

```go
items.GET("", controller.ListItems)                           // 传 1 个
items.POST("", middleware.JWTAuth(), controller.CreateItem)   // 传 2 个
```

#### ③ `gin.HandlerFunc` 是什么？—— **这就是"参数怎么定"的答案**

它是一个**函数类型**，Gin 源码里的定义是：

```go
type HandlerFunc func(*gin.Context)
```

翻译成人话：**"接受一个 `*gin.Context` 参数、没有返回值的函数"**。

所以，**只要你的函数长成这个样子，就能传进去**：

```go
func ListItems(c *gin.Context) { ... }          // ✅ 符合：1 个参数，无返回值
func ListItems(c *gin.Context) error { ... }    // ❌ 不符合：多了返回值
func ListItems() { ... }                         // ❌ 不符合：没有参数
func ListItems(c *gin.Context, x int) { ... }   // ❌ 不符合：参数太多
```

打开 `controller/item_controller.go` 验证一下：

```go
func ListItems(c *gin.Context) {    // ← 和 HandlerFunc 的定义一模一样
    ...
}
```

> **所以"函数参数是怎么定的"这个问题的答案是**：
> **不是我们定的，是 Gin 在源码里规定好的，我们照着它的要求写函数。**
>
> 就像插座规定了插头的形状 —— 你的插头必须长成那个样子才能插进去。
> 用术语说，这叫"**实现了 `gin.HandlerFunc` 这个类型**"。

#### ④ 为什么中间件能和处理函数写在同一个调用里？

```go
items.POST("", middleware.JWTAuth(), controller.CreateItem)
//                 ↑ 第 1 个 handler      ↑ 第 2 个 handler
```

因为 `handlers` 是**变长参数**，传多个就**按顺序依次执行**：

```
请求进来
   ↓
执行 JWTAuth（第 1 个）
   ├─ 验过了 → 内部调用 c.Next() → 继续往下
   └─ 没验过 → 内部调用 c.Abort() → 到此为止，后面不执行
   ↓
执行 CreateItem（第 2 个）
```

**关键认知**：所谓"中间件"，**不是什么特殊的东西** ——
它就是一个**普通的处理函数**，只不过被放在列表的**前面**，
而且内部会调用 `c.Next()`（放行）或 `c.Abort()`（拦下）。

#### ⑤ 那一对大括号 `{ }` 是干嘛的？

```go
items := api.Group("/items")
{
    items.GET("", controller.ListItems)
    items.POST("", middleware.JWTAuth(), controller.CreateItem)
}
```

**纯粹为了好看，没有实际作用**，删掉照样能跑。

它是 Go 的**块语法**：把一组语句包起来，缩进之后**一眼看出"这些路由是同一组的"**。

### 2.1.5 小结：Gin 到底帮你做了什么

| 没有 Gin | 有 Gin |
|---|---|
| 自己解析 HTTP 请求原文 | 已经解析好了，`c` 里什么都有 |
| 自己写 if-else 匹配 URL | 注册一次，请求来了自动匹配 |
| 自己处理路径参数 `:id` | `c.Param("id")` 一行取出 |
| 自己把结构体转成 JSON | `c.JSON(200, obj)` 一行 |
| 自己实现"中间件"机制 | 写个普通函数，放进 handlers 列表就行 |

## 2.2 GORM —— 管"数据库"的

**问题**：数据存在 MySQL 里，Go 代码怎么跟它说话？

**笨办法**：手写 SQL 字符串。

```go
// 不用 GORM 的话，你得这么写（还得自己处理结果、防注入、拼参数……）
rows, _ := db.Query("INSERT INTO items (title, type) VALUES (?, ?)", title, type)
```

**用 GORM**：

```go
// dao/item_dao.go
func CreateItem(item *models.Item) error {
    return DB.Create(item).Error
}
```

一行搞定。GORM 会自动：

1. 看懂你传进来的 `item` 结构体
2. 生成对应的 SQL（`INSERT INTO items (...) VALUES (...)`）
3. 执行它
4. 把数据库生成的 ID 填回 `item.ID`

> **GORM 叫 ORM**（Object-Relational Mapping，对象关系映射）。
> 一句话：**让你用"操作 Go 对象"的方式操作数据库表**，不用手写 SQL。

## 2.3 JWT —— 管"身份"的

**问题**：HTTP 是"无记忆"的 —— 你登录了，但下一个请求过来，服务器怎么知道"你就是刚才登录的那个人"？

**答案**：登录成功后，服务器发给你一张"**通行证**"（就是 token），
之后你每次请求都带上它，服务器一看就知道你是谁。

这张通行证就是 **JWT**（JSON Web Token），长得像一串乱码：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjozLCJ1c2VybmFtZSI6ImRlbW8iLCJleHAiOjE3OTE4NjI0MzB9.JSq56Xlyq-eSLEuNzfZeFt1xYZwkeWV_MbVt3-uR9CE
```

它其实是用 `.` 分成三段的：

| 段 | 内容 | 能不能被看到 |
|---|---|---|
| 第 1 段 | 说明用什么算法签名 | 能（就是 Base64 编码，不是加密） |
| 第 2 段 | **真正的数据**：用户 ID、用户名、过期时间 | 能（同上） |
| 第 3 段 | **签名**：用密钥算出来的"防伪标记" | 不能伪造 |

**关键点**：前两段谁都能解开看（所以**别往 token 里放密码**），
但**第三段伪造不了** —— 因为算签名需要一个只有服务器知道的"密钥"。
服务器收到 token 时重新算一遍签名，对不上就说明这 token 是假的或被改过。

## 3.1 结构体 struct —— 把数据打包

**问题**：一个"用户"有用户名、密码、昵称……怎么把它们打包成一个整体？

**答案**：结构体。

```go
// models/user.go
type User struct {
    ID       uint
    Username string
    Password string
}
```

读法：`type User struct { ... }` = "定义一个新类型，叫 User，它包含这些字段"。

用起来：

```go
var u User            // 造一个空的 User
u.Username = "小明"    // 用点号访问字段
```

**重要规则：字段名首字母大写 = 公开，小写 = 私有。**

```go
type User struct {
    Username string   // 大写 → 别的包能访问 ✅
    password string   // 小写 → 只有 models 包自己能访问 ❌
}
```

> 为什么？Go 用大小写来控制"能不能被外部访问"（其他语言里通常写 `public` / `private` 关键字）。
> **我们的字段全部大写**，因为 controller、service、dao 都要访问它们。

## 3.2 struct tag —— 给字段贴标签

结构体字段后面反引号里的东西，叫 **tag（标签）**：

```go
// models/item.go
Title    string `gorm:"type:varchar(64);not null" json:"title"`
Contact  string `gorm:"type:varchar(100);not null" json:"-"`
```

**怎么理解**：就像给一个箱子贴了好几张标签，**不同的工具看不同的标签**：

| 标签 | 谁在看 | 作用 |
|---|---|---|
| `gorm:"..."` | GORM（数据库） | 建表时这一列叫什么类型、能不能为空 |
| `json:"..."` | 序列化（转成 JSON 时） | 这个字段输出成什么名字 |

**举个例子**：

```go
Username string `gorm:"type:varchar(32)" json:"username"`
```

- 数据库里：列名叫 `username`（GORM 默认把 `Username` 转成下划线小写），类型 `varchar(32)`
- 返回给前端：`"username": "小明"`

**如果 `json:"-"` 呢？**

```go
Password string `gorm:"type:varchar(100)" json:"-"`
```

`json:"-"` 的意思是：**转成 JSON 时，永远跳过这个字段**。

> 这是本项目最重要的一个技巧，第六章 6.2 会详细讲 ——
> 它让"密码"和"联系方式"**根本不可能**被泄露出去。

## 3.3 指针 `&` 和 `*` —— 房间号 vs 搬整个房间

这是新手最容易懵的概念，用比喻讲。

**场景**：你要把"一个用户的信息"交给别人。

**方式一：复制一份给他**（值传递）

```go
func showUser(u User) {   // 注意：没有星号
    // 这里拿到的是 User 的一份完整拷贝
    // 改动 u，不会影响原来的那个
}
```

好比：**把整个房间的东西搬一份到新房间**。安全，但如果房间很大，搬起来很费劲。

**方式二：告诉他房间号**（指针传递）

```go
func showUser(u *User) {  // 注意：有星号
    // 这里拿到的是"地址"，顺着地址能找到原来那个 User
    // 改动 u.Username，原来的也会变
}
```

好比：**只给他一个门牌号**。省事，而且他能直接进房间改东西。

**两个符号**：

| 符号 | 名字 | 意思 | 例子 |
|---|---|---|---|
| `*` | 解引用 / 声明指针类型 | "指向某个东西的地址" | `*User` = 指向 User 的指针 |
| `&` | 取地址 | "把这个东西的地址给我" | `&user` = user 的地址 |

**在我们的代码里**：

```go
// dao/item_dao.go
func GetItemByID(id uint) (*models.Item, error) {
    var item models.Item
    DB.First(&item, id)      // &item：把 item 的地址给 GORM，让它把查到的数据填进去
    return &item, nil        // 返回地址，而不是复制整个结构体
}
```

> **为什么查询要传 `&item`？**
> 因为 GORM 需要**往你的变量里写数据**。如果传的是拷贝，它写进拷贝里，
> 你原来的 `item` 还是空的 —— 这就是"要传地址"的原因。

## 3.4 方法 —— 给类型配一个专属函数

普通函数：

```go
func DSN(m MySQLConfig) string { ... }    // 调用：DSN(cfg.MySQL)
```

方法（多了一个"接收者"）：

```go
// config/config.go
func (m MySQLConfig) DSN() string { ... }  // 调用：cfg.MySQL.DSN()
```

区别就是函数名前面多了个 `(m MySQLConfig)`。

**怎么理解**：`(m MySQLConfig)` 里的 `m` 就是"这个对象自己"，
方法体里可以直接用 `m.Host`、`m.Port` 这些字段。

> 好比：`func 走路(人)` 是普通函数，`func (人) 走路()` 是方法 —— 走路是"人"这个类型自带的能力。
> 我们的项目里方法用得不多，主要是 `config.go` 里的 `DSN()`。

## 3.5 闭包 —— 能"记住"东西的函数

**普通函数**：给什么用什么，用完就忘。

**闭包**：函数里"记住"了外面的一些变量。

```go
// dao/item_dao.go（简化版）
build := func() *gorm.DB {
    tx := DB.Model(&models.Item{})
    if q.Keyword != "" {
        tx = tx.Where("title LIKE ?", "%"+q.Keyword+"%")   // ← 用到了外面的 q
    }
    return tx
}
```

这里的 `build` 就是一个闭包 —— 它记住了外面的 `q`（查询条件），
每次调用它，都能按 `q` 里的条件拼出查询。

**项目里两处用到闭包**：

| 位置 | 为什么用闭包 |
|---|---|
| `dao/item_dao.go` 的 `build` | 同样的查询条件要用两次（一次数总数、一次取数据），抽成闭包不用重复写 |
| `middleware/auth.go` 的 `JWTAuth()` | 它**返回一个函数**，而不是自己当处理函数（下一节细讲） |

## 3.6 接口 interface —— `any` 和 `error`

Go 里有两个你一定会反复见到的"接口"：

### `any`（= `interface{}`）

意思是"**任意类型**"。

```go
// utils/response.go
type Response struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Data    any    `json:"data"`     // ← 这里能装任何东西
}
```

因为 `data` 有时候要装用户、有时候要装帖子、有时候要装列表，
所以声明成 `any`（什么都能装）。

### `error`

Go 处理错误的方式很特别：**错误就是一个普通的值**，用返回值往外传。

```go
func CreateItem(item *models.Item) error {
    return DB.Create(item).Error    // 成功返回 nil，失败返回错误
}
```

用的时候：

```go
err := dao.CreateItem(item)
if err != nil {          // nil 表示"没有错误"
    // 出错了，处理它
}
```

> 这就是为什么代码里到处都是 `if err != nil` —— 这不是啰嗦，
> 而是 Go 的设计哲学：**错误必须被显式处理，不能假装没看见**。

## 3.7 哨兵错误 —— 怎么区分"哪种错误"

`err != nil` 只能知道"出错了"，但出的是哪种错？

我们的做法：**预先定义几个"标准错误"**，然后比较。

```go
// service/errors.go
var (
    ErrUsernameTaken    = errors.New("用户名已被注册")
    ErrWrongCredentials = errors.New("用户名或密码错误")
    ErrItemNotFound     = errors.New("信息不存在")
    ErrNotOwner         = errors.New("只能操作自己发布的信息")
    ErrStatusBackward   = errors.New("状态只能前进，不能回退")
    ErrBadTime          = errors.New("时间格式不正确")
)
```

用的时候：

```go
// controller/item_controller.go
if errors.Is(err, service.ErrNotOwner) {
    utils.Fail(c, utils.CodeForbidden, err.Error())   // 翻译成 403
    return
}
```

> `errors.Is(错误A, 错误B)` = "A 是不是就是 B 这种错误？"
> 这些预定义好的错误值，行话叫"**哨兵错误**"（sentinel error）。

**为什么要这样？** 因为不同的错误要返回不同的 HTTP 状态码：

| 错误 | 翻译成 | 状态码 |
|---|---|---|
| `ErrItemNotFound` | "信息不存在" | 404 |
| `ErrNotOwner` | "只能操作自己发布的信息" | 403 |
| `ErrStatusBackward` | "状态只能前进，不能回退" | 400 |
| `ErrBadTime` | "时间格式不正确" | 400 |

# 第四章 一次请求的完整旅程（★ 最重要）

前三章分别讲了 HTTP 协议、三个工具（Gin / GORM / JWT）、Go 语法。这一章把它们装起来，跟着两条真实请求走一遍：

- **例一：小明发布失物帖**（`POST /api/items`）—— 写操作，需要登录，七层全走
- **例二：小红搜索"校园卡"**（`GET /api/items?keyword=校园卡`）—— 读操作，公开接口，重点看 SQL 是怎么拼出来的

每个例子开头先给"**数据传输总览**"：数据在各层之间是什么形态、怎么变形。然后按步骤展开，每一步贴出这一步执行的**完整代码**，再逐行说明。

## 4.1 例一：小明发布失物帖

### 4.1.1 总览：数据在这次请求里怎么流动

小明的操作：在发布页填完表单、点了"发布"按钮。从这一刻到数据存进 MySQL，"校园卡"这条信息**一共变了六次形态**：

```
① 浏览器 JS 对象
   {type: "lost", title: "校园卡", category: "card", ...}
        │  fetch 序列化成 JSON 文本 + HTTP 传输
        ▼
② HTTP 请求（纯文本，走在网络上）
   POST /api/items
   Authorization: Bearer eyJhbGci...
   {"type":"lost","title":"校园卡",...}
        │  Gin 解析请求体（JSON 文本 → Go 结构体）
        ▼
③ controller 里的 CreateItemRequest 结构体
   {Type: "lost", Title: "校园卡", Category: "card", ...}
        │  service 组装：补上 token 里的 userID、写死初始状态
        ▼
④ service 里的 Item 结构体（"数据库模型"）
   {Type: "lost", Title: "校园卡", ..., Status: "searching", UserID: 3}
        │  GORM 翻译成 SQL
        ▼
⑤ INSERT 语句（dao）
   INSERT INTO items (type, title, ..., status, user_id) VALUES (...)
        │  MySQL 执行
        ▼
⑥ items 表里的一行
   id=4（自增分配）, title='校园卡', status='searching', user_id=3
        │  自增 ID 回填 → 逐层返回 → JSON 序列化
        ▼
⑦ HTTP 响应（走在网络上，原路返回）
   {"code":0,"message":"发布成功","data":{"id":4,"title":"校园卡",...}}
        │  浏览器解析
        ▼
   浏览器 JS 对象（前端拿到新帖数据）
```

**三次关键变形**（后面各步会详细展开）：

| 变形 | 发生在哪一步 | 靠什么完成 |
|---|---|---|
| JSON 文本 → Go 结构体 | 第 4 步（controller） | `c.ShouldBindJSON(&req)` |
| Go 结构体 → SQL | 第 6 步（dao） | GORM 的 `DB.Create(item)` |
| Go 结构体 → JSON 文本 | 第 7 步（controller） | `c.JSON(...)` |

另外注意两个**凭空多出来**的字段：`user_id` 不是前端传的（来自 token），`id` 不是代码写的（MySQL 自增后回填）。它们在数据流里"半路加入"。

下面按七步走一遍，每步都标注**数据在这一步发生了什么变化**。

### 4.1.2 前置：小明已经登录

登录接口返回给他的 token：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjozLCJ1c2VybmFtZSI6ImRlbW8iLCJleHAiOjE3OTE4NjI0MzB9.JSq56Xlyq...
```

三个部分用 `.` 隔开：头部（算法 HS256）、载荷（`user_id: 3`、`username: "demo"`、过期时间）、签名。前端把它存在浏览器里，之后每次请求自动带上 —— 这就是后面"中间件知道你是谁"的全部依据。

> 载荷只是 Base64 编码，**没有加密** —— 谁都能解码看到 `user_id: 3`。防的是"篡改"（改了签名就对不上），不是"偷看"。

### 4.1.3 第 1 步：浏览器发出请求

**数据变化**：JS 对象 → HTTP 请求文本（序列化 + 加请求头）。

前端把用户填的内容拼成 JSON，连同 token 一起发出去：

```http
POST /api/items HTTP/1.1
Host: localhost:8080
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Content-Type: application/json

{
  "type": "lost",
  "title": "校园卡",
  "category": "card",
  "campus": "下沙校区",
  "place": "图书馆二楼",
  "happened_at": "2026-10-05 14:30",
  "description": "黑色卡套，里面有校园卡和饭卡",
  "contact": "微信 xiaoming123"
}
```

这份请求告诉服务器四件事：

| 位置 | 内容 | 含义 |
|---|---|---|
| 请求行 | `POST /api/items` | **干什么**（新建）+ **找谁**（物品接口） |
| 请求头 | `Authorization: Bearer eyJ...` | **我是谁**（通行证） |
| 请求头 | `Content-Type: application/json` | 请求体是什么格式 |
| 请求体 | `{...}` JSON | **内容是什么** |

发出去之后，前端**什么都不做，等着**，直到收到响应。

> 注意请求体里**没有** `status` 和 `user_id` 字段 —— 前端根本没地方传这两个值（`CreateItemRequest` 结构体里没有它们）。状态和归属由后端决定，这是安全设计，第 5 步详细讲。

### 4.1.4 第 2 步：Gin 查路由表，找到处理函数

**数据变化**：无（这一步只是"决定谁来处理"，数据还没被碰）。

服务器收到请求，Gin 拿着 `POST /api/items` 去查启动时登记好的路由表。路由表就是 `router/router.go` 里 `Setup()` 注册的内容（物品模块部分）：

```go
// router/router.go（物品模块部分）
// 所有业务接口统一挂在 /api 下
api := r.Group("/api")

// ---------- 物品模块 ----------
items := api.Group("/items")
{
	items.GET("", controller.ListItems)                     // 列表（公开，支持搜索/筛选/分页）
	items.POST("", middleware.JWTAuth(), controller.CreateItem) // 发布（需登录）

	// ⚠️ /my 写在 /:id 前面：Gin 会优先匹配静态路由，但保持这个顺序更保险
	items.GET("/my", middleware.JWTAuth(), controller.MyItems) // 我的发布（需登录）

	items.GET("/:id", controller.GetItem)                                    // 详情（公开）
	items.GET("/:id/contact", middleware.JWTAuth(), controller.GetContact)   // 联系方式（需登录）
	items.PUT("/:id", middleware.JWTAuth(), controller.UpdateItem)           // 编辑（仅本人）
	items.PATCH("/:id/status", middleware.JWTAuth(), controller.UpdateStatus) // 改状态（仅本人）
	items.DELETE("/:id", middleware.JWTAuth(), controller.DeleteItem)        // 删除（仅本人）
}
```

**逐段说明**：

**`api := r.Group("/api")`**
- `Group` 是"分组"：给一组接口加共同前缀。建完之后写 `items.GET("")` 就等于 `GET /api/items`，不用每条都写全路径。

**`items := api.Group("/items")`**
- 再套一层分组，前缀变成 `/api` + `/items` = `/api/items`。

**`items.POST("", middleware.JWTAuth(), controller.CreateItem)`（命中行）**
- 三个部分：

| 位置 | 内容 | 含义 |
|---|---|---|
| 第 1 个参数 | `""` | 路径（空字符串 = 就用分组前缀本身，即 `/api/items`） |
| 第 2 个参数 | `middleware.JWTAuth()` | 中间件：进处理函数之前的"关卡" |
| 第 3 个参数 | `controller.CreateItem` | 真正的处理函数 |

- **有中间件 = 要登录，没有 = 不用登录**，看路由注册这一行就能判断。比如 `items.GET("", controller.ListItems)` 没有中间件 —— 列表是公开接口。

**Gin 的匹配结果**：`POST /api/items` 命中第 2 行 → 先过 `JWTAuth` 中间件，再到 `CreateItem`。

> `:id` 是**路径参数**，能匹配任意值：`GET /api/items/123` 命中 `items.GET("/:id", ...)`，代码里用 `c.Param("id")` 取出 `"123"`。完整的路由文件见 5.1。

---
### 4.1.5 第 3 步：中间件验明正身

**数据变化**：从 token 里**解出** `user_id: 3` 和 `username: "demo"`，存进本次请求的 Context（后面所有层都能取到）。

`JWTAuth` 的完整代码（`middleware/auth.go`）：

```go
package middleware

import (
	"strings"

	"lostfound/utils"

	"github.com/gin-gonic/gin"
)

// JWTAuth 认证中间件：挂在需要登录的接口前面，负责"验明正身"
//
// 为什么写成 func() gin.HandlerFunc（返回函数的函数，即闭包）而不是直接写处理函数？
// 因为中间件将来可能需要参数（比如权限等级），返回函数的形式可以带参数，
// 这是 Gin 社区的标准写法（本地李文周博客里也是这个签名）
func JWTAuth() gin.HandlerFunc {
	return func(c *gin.Context) {
		// 1. 从请求头里取 Authorization，格式规定为：Bearer <token>
		authHeader := c.GetHeader("Authorization")
		if authHeader == "" {
			utils.Fail(c, utils.CodeUnauthorized, "请先登录")
			c.Abort() // ★ 关键：终止后续处理函数，不写这行的话接口还会继续执行！
			return
		}

		// 2. 按空格切成两段，校验格式（SplitN 的 2 表示最多切一刀）
		parts := strings.SplitN(authHeader, " ", 2)
		if len(parts) != 2 || parts[0] != "Bearer" {
			utils.Fail(c, utils.CodeUnauthorized, "token 格式错误，应为：Bearer xxx")
			c.Abort()
			return
		}

		// 3. 解析 token（签名对不对？过期没有？）
		claims, err := utils.ParseToken(parts[1])
		if err != nil {
			utils.Fail(c, utils.CodeUnauthorized, "登录已过期，请重新登录")
			c.Abort()
			return
		}

		// 4. 把用户信息存进本次请求的上下文，后面的处理函数用 c.GetUint("user_id") 取
		//    （Context 相当于"这次请求的随身口袋"，中间件放进去，handler 拿出来）
		c.Set("user_id", claims.UserID)
		c.Set("username", claims.Username)

		c.Next() // 放行，交给下一个处理函数
	}
}
```

**逐段说明（跟着小明的这次请求走）**：

**`func JWTAuth() gin.HandlerFunc`**
- 注意它不是处理函数本身，而是**返回**处理函数的函数。调用 `JWTAuth()` 得到真正的中间件，Gin 拿它去执行。包这一层是为了将来能带参数（比如 `JWTAuth("admin")` 限定管理员）。

**第 1 段：取 token**
- `authHeader := c.GetHeader("Authorization")`：小明这次请求取到的是 `"Bearer eyJhbGciOiJIUzI1NiIs..."`。
- 如果小明没带（`authHeader == ""`）→ 返回 401「请先登录」，`c.Abort()` 拦下，后面的代码一行都不执行。

**第 2 段：校验格式**
- `strings.SplitN(authHeader, " ", 2)`：按空格切一刀，得到：
  ```
  parts[0] = "Bearer"
  parts[1] = "eyJhbGciOiJIUzI1NiIs..."
  ```
- 校验：必须切成 2 段，且第一段必须是 `Bearer`（HTTP 认证的标准写法）。

**第 3 段：验签**
- `utils.ParseToken(parts[1])`：拿 token 去 `utils/jwt.go` 验证三件事 —— **验签名**（用密钥重算一遍，对不上说明被伪造/篡改）、**验过期**（检查 `exp` 字段）、**取出数据**（把 `user_id`、`username` 拿出来）。
- 小明这次验签通过，得到 `claims.UserID = 3`、`claims.Username = "demo"`。
- 失败（被篡改或过期）→ 401「登录已过期，请重新登录」，`Abort()` 拦下。

**第 4 段：把身份放进 Context**
- `c.Set("user_id", 3)`：**关键一步**。中间件和后面的处理函数是两个不同的函数，没法直接传变量；Context 就是它们之间的传递通道 —— 中间件放进去，controller 用 `c.GetUint("user_id")` 取出来。
- 这个 `3` 是从 **token 的签名内容**里解出来的，不是前端传的字段。后面 service 组装数据时用它当发布者 ID —— **身份不可伪造的根基就在这里**。

**第 5 段：放行**
- `c.Next()`：交给下一个函数（`controller.CreateItem`）。

**如果验不过会怎样**：三个失败分支都是同样的三件套 —— 发 401 响应 → `c.Abort()` → `return`。`c.Abort()` 最容易漏：不写它的话，虽然响应已经发了 401，**处理函数还会继续执行** —— 会出现"未登录却把帖子删了"这种事故。

### 4.1.6 第 4 步：controller 收参数

**数据变化**：JSON 文本 → `CreateItemRequest` 结构体（按 `json` 标签逐字段填充 + 按 `binding` 标签校验）。

`CreateItem` 的完整代码（`controller/item_controller.go` 的一部分）：

```go
// CreateItem 处理 POST /api/items —— 发布（需登录）
func CreateItem(c *gin.Context) {
	var req models.CreateItemRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	userID := c.GetUint("user_id")
	item, err := service.CreateItem(userID, req)
	if err != nil {
		handleItemError(c, err)
		return
	}
	utils.OKMsg(c, "发布成功", item)
}
```

它用到的请求结构体（`models/item.go` 的一部分）：

```go
// CreateItemRequest 发布请求体
type CreateItemRequest struct {
	Type        ItemType `json:"type" binding:"required,oneof=lost found"`
	Title       string   `json:"title" binding:"required,max=64"`
	Category    string   `json:"category" binding:"required,oneof=card electronics books clothing daily other"`
	Campus      string   `json:"campus" binding:"max=32"`
	Place       string   `json:"place" binding:"max=64"`
	HappenedAt  string   `json:"happened_at" binding:"required"` // 用字符串收，service 里再解析成时间（前端格式五花八门）
	Description string   `json:"description" binding:"max=500"`
	Contact     string   `json:"contact" binding:"required,max=100"`
}
```

**逐段说明**：

**`var req models.CreateItemRequest`**
- 声明一个空结构体，等着接数据。

**`c.ShouldBindJSON(&req)` —— 一行干两件事**
- **解析**：把请求体 JSON 文本按 `json:"xxx"` 标签填进结构体字段。小明这次的结果：
  ```
  "title":"校园卡"  →  req.Title = "校园卡"
  "type":"lost"     →  req.Type = "lost"
  "happened_at":"2026-10-05 14:30"  →  req.HappenedAt = "2026-10-05 14:30"（还是字符串）
  ```
- **校验**：按 `binding:"..."` 标签检查每个字段：

| 规则 | 含义 | 例子 |
|---|---|---|
| `required` | 必填 | `title` 不传就报错 |
| `max=64` | 长度上限 | `title` 超过 64 字符报错 |
| `oneof=lost found` | 枚举值 | `type` 只能是这两个之一 |

- 有一样不合格就返回 400，**不往下走** —— 后面的 service 可以放心假设"数据格式是干净的"。
- 传 `&req`（取地址）的原因：要把数据**写进** `req`，传拷贝的话写进去也拿不到。
- 注意：`binding` 校验只保证"格式合法"，不保证"业务合法"。比如 `category` 传 `"other"` 是合法的，但"这个帖子该不该由小明发"是 service 的判断。

**`userID := c.GetUint("user_id")`**
- 从 Context 取中间件放的 `3`。
- 用 `GetUint` 而不是 `Get`：`Get` 返回 `any`（任意类型）还得自己转，`GetUint` 直接返回 `uint`，取不到就返回 0。

**`item, err := service.CreateItem(userID, req)`**
- 把活交给下一层。注意**两个参数的可信度不同**：
  - `userID` = `3` —— 从 token 验签解出来的（**可信**）
  - `req` —— 从请求体来的（**不可信**，用户想传什么就传什么）

**`utils.OKMsg(c, "发布成功", item)`**
- 成功响应（第 7 步展开）。如果 service 返回错误（比如时间格式不对），走 `handleItemError` 翻译成对应状态码。

**controller 的定位**：只做三件事 —— 收参数 → 调 service → 发响应。它**不写业务逻辑**（"新帖状态必须是寻找中"这种规则不在这），那是 service 的活。

### 4.1.7 第 5 步：service 做业务

**数据变化**：`CreateItemRequest` 结构体 → `Item` 结构体。三处变化：时间字符串转成 `time.Time`、补上 `Status: "searching"`、补上 `UserID: 3`。

`CreateItem` 的完整代码（`service/item_service.go` 的一部分）：

```go
// CreateItem 发布：解析时间 → 组装 → 入库
func CreateItem(userID uint, req models.CreateItemRequest) (*models.Item, error) {
	happenedAt, err := utils.ParseTime(req.HappenedAt)
	if err != nil {
		return nil, ErrBadTime
	}

	item := &models.Item{
		Type:        req.Type,
		Title:       req.Title,
		Category:    models.ItemCategory(req.Category),
		Campus:      req.Campus,
		Place:       req.Place,
		HappenedAt:  happenedAt,
		Description: req.Description,
		Contact:     req.Contact,
		Status:      models.StatusSearching, // 新帖一律从"寻找中"开始
		UserID:      userID,
	}
	if err := dao.CreateItem(item); err != nil {
		return nil, err
	}
	return item, nil
}
```

它用到的时间解析工具（`utils/time.go` 完整）：

```go
package utils

import (
	"fmt"
	"time"
)

// timeLayouts 前端可能传来的几种时间格式，挨个尝试
// Go 的时间格式不用 yyyy-MM-dd，而是用"参考时间" 2006-01-02 15:04:05 来当模板（记住这个数就行）
var timeLayouts = []string{
	time.RFC3339,          // 2026-09-26T14:30:00+08:00
	"2006-01-02T15:04:05", // 2026-09-26T14:30:00
	"2006-01-02T15:04",    // 2026-09-26T14:30（<input type="datetime-local"> 的原生格式）
	"2006-01-02 15:04:05", // 2026-09-26 14:30:00
	"2006-01-02 15:04",    // 2026-09-26 14:30
	"2006-01-02",          // 2026-09-26
}

// ParseTime 把前端传来的时间字符串解析成 time.Time
func ParseTime(s string) (time.Time, error) {
	for _, layout := range timeLayouts {
		// ParseInLocation：按本地时区解析（不加这个，时间会差 8 小时）
		if t, err := time.ParseInLocation(layout, s, time.Local); err == nil {
			return t, nil
		}
	}
	return time.Time{}, fmt.Errorf("无法识别的时间格式: %s", s)
}
```

**逐段说明**：

**`happenedAt, err := utils.ParseTime(req.HappenedAt)`**
- 小明的 `req.HappenedAt` 是字符串 `"2026-10-05 14:30"`，但数据库列是时间类型，要转换。
- `ParseTime` 把 6 种常见格式挨个试（`timeLayouts`），哪个解析成功用哪个。小明这个匹配 `"2006-01-02 15:04"` 这一行，得到 `2026-10-05 14:30:00 +0800 CST`。
- 全试完都不行 → 返回错误，service 转成 `ErrBadTime`（controller 翻译成 400）。
- 为什么用字符串收时间而不是让 `ShouldBindJSON` 直接绑 `time.Time`：前端格式不可控（`datetime-local` 控件给 `2026-10-05T14:30`，手输可能给 `2026-10-05`），字符串收、这里统一转换，兼容性最好。

**组装 `models.Item` —— 重点看两行"后端强制"**

```go
Status: models.StatusSearching, // 新帖一律从"寻找中"开始
UserID: userID,                 // 发布者 = 当前登录用户（token 里的 3）
```

| 字段 | 前端能传吗 | 为什么 |
|---|---|---|
| `Status` | 不能 | 新帖必须从"寻找中"开始，否则有人一发布就是"已结束" |
| `UserID` | 不能 | 只能取 token 里解出来的 ID。如果让前端传，**任何人都能冒充别人发帖** |

- 其余字段都是从 `req` 抄过来的（那些本来就是用户填的内容，抄过来没问题）。
- `Category: models.ItemCategory(req.Category)`：一次类型转换 —— `req.Category` 是普通 `string`，`Item.Category` 是 `ItemCategory` 类型（`type ItemCategory string`），要显式转。

**`if err := dao.CreateItem(item); err != nil { return nil, err }`**
- 交给下一层存库。出错就原样往上传（controller 会翻译成 500）。
- 注意返回值 `(*models.Item, error)`：Go 的函数可以返回多个值，这里同时返回"结果"和"错误"，调用方先看 `err` 是不是 nil。

### 4.1.8 第 6 步：dao 存进数据库

**数据变化**：`Item` 结构体 → INSERT 语句 → `items` 表里的一行。同时 MySQL 分配自增 ID，GORM 把它**回填**到 `item.ID`。

`CreateItem` 的完整代码（`dao/item_dao.go` 的一部分）：

```go
// CreateItem 新增帖子
func CreateItem(item *models.Item) error {
	return DB.Create(item).Error
}
```

**就一行，拆开看**：

| 部分 | 含义 |
|---|---|
| `DB` | 全局数据库连接（启动时由 `main.go` 通过 `dao.InitDB(db)` 注入） |
| `.Create(item)` | GORM 的方法：把结构体插入数据库 |
| `.Error` | GORM 把错误存在 `.Error` 字段里，取出来当返回值 |

**GORM 在背后生成的 SQL**：

```sql
INSERT INTO items
  (type, title, category, campus, place, happened_at,
   description, contact, image_url, status, user_id, created_at, updated_at)
VALUES
  ('lost', '校园卡', 'card', '下沙校区', '图书馆二楼', '2026-10-05 14:30:00',
   '黑色卡套...', '微信 xiaoming123', '', 'searching', 3, NOW(), NOW());
```

**两个自动发生的事**：

1. **`created_at` / `updated_at` 自动填**：GORM 认得出这两个名字特殊的字段，插入时自动填当前时间，不用代码赋值。
2. **自增 ID 回填**：MySQL 分配 `id=4` 后，GORM 自动把它写回 `item.ID`。所以第 7 步返回的 JSON 里能看到 `"id": 4` —— 这个值是数据库给的，不是 Go 代码写的。

> 注意 `contact` 这一列**正常入库**了（`gorm` 标签不受影响）—— 它在数据库里，只是返回给前端时会被剔除（第 7 步讲）。

### 4.1.9 第 7 步：返回响应

**数据变化**：`Item` 结构体 → JSON 文本 → HTTP 响应 → 浏览器 JS 对象。**`contact` 字段在这一步消失**。

回到 controller 的最后一行：

```go
utils.OKMsg(c, "发布成功", item)
```

它调用的函数（`utils/response.go` 的一部分）：

```go
// Response 是所有接口统一的响应结构
// 字段名首字母大写才能被 JSON 序列化；`json:"xxx"` 决定输出时的 key 名
type Response struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data"` // any 是 interface{} 的简写（Go 1.18+），表示"任意类型"
}

// OKMsg 成功响应（自定义 message）
func OKMsg(c *gin.Context, message string, data any) {
	c.JSON(http.StatusOK, Response{Code: CodeSuccess, Message: message, Data: data})
}
```

**逐段说明**：
- `Response{Code: 0, Message: "发布成功", Data: item}`：把 `item` 套进统一格式。`Data any` 表示"任意类型"，列表接口塞数组、这里塞单个对象，共用一个字段。
- `c.JSON(http.StatusOK, ...)`：Gin 的方法 —— 把结构体**按 `json` 标签序列化成 JSON 文本**，作为响应体发回去。
- 返回路径是**原路返回**：dao → service → controller → 响应。每一层只管把结果往上传，不关心上面怎么用。

**最终发出去的响应**：

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"code":0,"message":"发布成功","data":{"id":4,"type":"lost","title":"校园卡","category":"card","campus":"下沙校区","place":"图书馆二楼","happened_at":"2026-10-05T14:30:00+08:00","description":"黑色卡套，里面有校园卡和饭卡","image_url":"","status":"searching","user_id":3,"created_at":"2026-10-06T11:33:51.132+08:00","updated_at":"2026-10-06T11:33:51.132+08:00"}}
```

前端拿到后，`data.id = 4` 就是新帖的 ID，可以拿它跳转到详情页。

### 4.1.10 细节：返回的 JSON 里为什么没有 `contact`

小明明明填了 `contact`（"微信 xiaoming123"），数据库也存了，为什么响应里没有？

因为 `models.Item` 给这个字段加了 `json:"-"`：

```go
// ★ 关键设计：contact 加了 json:"-"，任何返回 Item 的接口都**不可能**泄露联系方式
//   想拿到联系方式只能走 GET /api/items/:id/contact（需登录）—— 从结构上保证"登录可见"
Contact  string     `gorm:"type:varchar(100);not null" json:"-"`
```

| 操作 | contact 会怎样 |
|---|---|
| 存进数据库 | 正常存（`gorm` 标签不受 `json:"-"` 影响） |
| 序列化成 JSON | **永远跳过**（`json:"-"` 挡住） |

**这就是"未登录看不到联系方式"的实现方式** —— 不是"查出来再删掉"，而是**从结构上就不可能输出**。任何返回 `Item` 的接口（列表、详情、发布、编辑）都自动不带它。

想拿到联系方式？只能走专门的接口 `GET /api/items/:id/contact`（它挂了登录中间件，且单独返回 `contact` 字段）。

> 如果哪天在列表接口里手滑把 contact 也返回了，等于把全站用户的微信号公开 —— PRD 的验收点直接失败。`json:"-"` 从根上杜绝这种失误。

## 4.2 例二：小红搜索"校园卡"

例一是**写**（POST，需要登录），例二是**读**（GET，公开接口），重点看两件事：查询参数怎么从 URL 里取出来、SQL 是怎么按条件拼出来的。

### 4.2.1 总览：数据在这次请求里怎么流动

```
① 浏览器 JS
   fetch("/api/items?keyword=校园卡&page=1&page_size=10")
        │  中文被浏览器 URL 编码
        ▼
② HTTP 请求（纯文本）
   GET /api/items?keyword=%E6%A0%A1%E5%9B%AD%E5%8D%A1&page=1&page_size=10
        │  Gin 解析 URL（自动解码中文）
        ▼
③ controller 里的 ItemListQuery 结构体
   {Keyword: "校园卡", Status: "searching", Page: 1, PageSize: 10}
        │  原样往下传（service 只是转发）
        ▼
④ dao 按条件拼出 SQL
   第一次：SELECT COUNT(*) FROM items WHERE ...    →  total = 3
   第二次：SELECT * FROM items WHERE ... ORDER BY created_at DESC LIMIT 10 OFFSET 0
        │  MySQL 执行
        ▼
⑤ 结果往回传
   []models.Item（2 条记录） + total（3）
        │  JSON 序列化
        ▼
⑥ HTTP 响应
   {"code":0,"message":"ok","data":{"list":[...],"total":3,"page":1,"page_size":10}}
        │  浏览器解析
        ▼
   前端渲染：2 张卡片 + "共 3 条"（知道还有下一页）
```

**和例一的对比**：

| | 例一（发布） | 例二（搜索） |
|---|---|---|
| 数据从哪来 | **请求体**（JSON） | **URL**（问号后面的查询参数） |
| 怎么取 | `c.ShouldBindJSON(&req)` | `c.Query("keyword")` |
| 需要登录 | 是（挂了中间件） | 否（公开） |
| 数据形态变化 | 六次 | 三次（没写数据库） |

### 4.2.2 请求

```http
GET /api/items?keyword=%E6%A0%A1%E5%9B%AD%E5%8D%A1&page=1&page_size=10
```

- `?` 后面是**查询参数**，`&` 分隔多个，`=` 连接名字和值。这次带了三个：`keyword`、`page`、`page_size`。
- `%E6%A0%A1%E5%9B%AD%E5%8D%A1` 是"校园卡"的 **URL 编码**：URL 里不能直接放中文，浏览器会自动编码、Gin 会自动解码，代码里拿到的还是 `"校园卡"`，不用手动处理。

### 4.2.3 第 1 步：路由匹配

**数据变化**：无。

```go
items.GET("", controller.ListItems)
```

这一行**没有中间件** —— 因为列表是公开接口，不登录也能看。对比例一的 `items.POST("", middleware.JWTAuth(), controller.CreateItem)`：**有中间件 = 要登录，没有 = 不用登录**。

### 4.2.4 第 2 步：controller 解析查询参数

**数据变化**：URL 里的字符串 → `ItemListQuery` 结构体。

`ListItems` 的完整代码（`controller/item_controller.go` 的一部分）：

```go
// ListItems 处理 GET /api/items —— 公开列表（搜索 / 筛选 / 分页）
func ListItems(c *gin.Context) {
	page, pageSize := parsePagination(c)

	// 状态默认只看"寻找中"（PRD 4.3：首页默认展示寻找中的信息）
	// 传 status=all 或 status=（空）表示不限状态
	status := c.DefaultQuery("status", string(models.StatusSearching))
	if status == "all" {
		status = ""
	}

	items, total, err := service.ListItems(models.ItemListQuery{
		Keyword:  c.Query("keyword"),  // 关键词模糊搜索
		Type:     c.Query("type"),     // lost / found
		Category: c.Query("category"), // card / electronics / ...
		Campus:   c.Query("campus"),
		Place:    c.Query("place"),
		Status:   status,
		Page:     page,
		PageSize: pageSize,
	})
	if err != nil {
		utils.Fail(c, utils.CodeServerError, "查询失败")
		return
	}

	// 返回 total 供前端判断"还有没有下一页"（上拉加载更多）
	utils.OK(c, gin.H{
		"list":      items,
		"total":     total,
		"page":      page,
		"page_size": pageSize,
	})
}
```

它用到的分页辅助函数（同文件）：

```go
// parsePagination 解析分页参数，带默认值和上限保护（防止有人传 page_size=999999）
func parsePagination(c *gin.Context) (int, int) {
	page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
	pageSize, _ := strconv.Atoi(c.DefaultQuery("page_size", "10"))
	if page < 1 {
		page = 1
	}
	if pageSize < 1 || pageSize > 50 {
		pageSize = 10
	}
	return page, pageSize
}
```

**逐段说明**：

**`page, pageSize := parsePagination(c)`**
- 小红这次 URL 里 `page=1&page_size=10`，解析出来就是 `1` 和 `10`。
- `c.DefaultQuery("page", "1")`：取 URL 参数，**没传时用默认值**。返回值是字符串（URL 里一切都是字符串）。
- `strconv.Atoi`：字符串转整数。`_` 忽略转换错误 —— 传了非数字（比如 `page=abc`）时 Atoi 返回 0，下面 `page < 1` 会兜成 1。
- `pageSize` 的上限 50：不设的话，有人传 `page_size=999999` 就能一次把全库拉走、把服务器拖垮。

**`status := c.DefaultQuery("status", string(models.StatusSearching))`**
- 小红没传 `status`，所以默认 `"searching"` —— 这就是"首页默认只显示寻找中的信息"的实现。
- 传 `status=all` 时置空字符串：空字符串在 dao 里表示"这个条件不用"（不限状态）。

**组装 `models.ItemListQuery`**
- 把 URL 上的筛选条件一个个取出来，装进一个结构体，一次往下传。
- 小红这次的结果：
  ```
  Keyword: "校园卡"（Gin 已自动解码）
  Type/Category/Campus/Place: ""（没传 → 空字符串 → dao 里跳过这些条件）
  Status: "searching"
  Page: 1, PageSize: 10
  ```
- `c.Query("keyword")` 和 `c.DefaultQuery` 的区别：前者没传返回空字符串，后者没传返回你指定的默认值。

**`utils.OK(c, gin.H{...})`**
- 返回 `{list, total, page, page_size}`。`gin.H` 是 `map[string]any` 的简写。
- 为什么要 `total`：前端拿 `total=3` 和当前 `list` 的条数（2 条）对比，就知道"还有下一页"，能做出"上拉加载更多"。

### 4.2.5 第 3 步：dao 拼 SQL（★ 本节重点）

**数据变化**：`ItemListQuery` 结构体 → 两条 SQL 语句 → MySQL 返回"总数 + 当页记录"。

`ListItems` 的完整代码（`dao/item_dao.go`）：

```go
// ListItems 按条件分页查询，返回（当页数据, 总数, 错误）
func ListItems(q models.ItemListQuery) ([]models.Item, int64, error) {
	// build 是一个闭包（能"记住"外部变量的函数），每次调用都重新拼一遍查询条件。
	// 为什么要建两次？因为查总数和查数据是两条独立的 SQL，
	// 复用同一个 *gorm.DB 链条容易被前面的 Limit/Offset 污染
	// （初学者最经典的 bug：先 Limit 再 Count，total 永远等于 page_size）
	build := func() *gorm.DB {
		tx := DB.Model(&models.Item{})

		if q.Keyword != "" {
			// LIKE 模糊匹配：两端加 % 表示"包含"，物品名称或描述命中都算
			like := "%" + q.Keyword + "%"
			tx = tx.Where("title LIKE ? OR description LIKE ?", like, like)
		}
		if q.Type != "" {
			tx = tx.Where("type = ?", q.Type)
		}
		if q.Category != "" {
			tx = tx.Where("category = ?", q.Category)
		}
		if q.Campus != "" {
			tx = tx.Where("campus = ?", q.Campus)
		}
		if q.Place != "" {
			tx = tx.Where("place LIKE ?", "%"+q.Place+"%")
		}
		if q.Status != "" {
			tx = tx.Where("status = ?", q.Status)
		}
		if q.UserID != 0 {
			tx = tx.Where("user_id = ?", q.UserID)
		}
		return tx
	}

	// 1. 先数总数（前端靠它判断"还有没有下一页"）
	var total int64
	if err := build().Count(&total).Error; err != nil {
		return nil, 0, err
	}

	// 2. 再取当页数据：ORDER BY created_at DESC + LIMIT + OFFSET
	// ★ items 用 make(..., 0) 初始化而不是 var 声明：
	//   查不到数据时，前者序列化成 []，后者是 null —— 前端拿到 null 调 .map() 会直接崩
	items := make([]models.Item, 0)
	err := build().
		Order("created_at DESC").
		Limit(q.PageSize).
		Offset((q.Page - 1) * q.PageSize).
		Find(&items).Error
	if err != nil {
		return nil, 0, err
	}
	return items, total, nil
}
```

**逐段说明**：

**`build` 闭包（拼查询条件）**
- 闭包 = 能"记住"外部变量的函数。`build` 记住了参数 `q`，每次调用都**重新拼一遍** WHERE 条件。
- 每条 `if q.Xxx != ""`：条件为空就跳过。小红这次只有 `Keyword` 和 `Status` 非空，所以拼出来的条件只有两条：
  ```
  WHERE title LIKE '%校园卡%' OR description LIKE '%校园卡%' AND status = 'searching'
  ```
- `LIKE "%校园卡%"`：两端 `%` 是通配符，表示"包含这三个字"。`title LIKE ? OR description LIKE ?` = 标题**或**描述命中都算。
- 所有值都用 `?` 占位符传参，**绝不拼接字符串** —— 防 SQL 注入的关键（下面细讲）。

**为什么 `build()` 要调用两次（两条 SQL）**：
- 第一次 `build().Count(&total)`：`SELECT COUNT(*) ...`，数一共多少条 → `total = 3`。
- 第二次 `build().Order(...).Limit(...).Offset(...).Find(&items)`：取当页数据 → 2 条记录。
- 两条 SQL 的 WHERE 条件**一模一样**，抽成 `build()` 就不用把一堆 `if` 写两遍。
- 为什么不复用同一条查询链：GORM 的方法链是有状态的，先 `.Limit(10)` 再 `Count`，SQL 会变成 `SELECT COUNT(*) ... LIMIT 10` —— **total 永远等于 10**（经典的初学者 bug）。每次从零重建，互不污染。

**`Order("created_at DESC")`**：按创建时间倒序（新的在前）。

**`Limit` / `Offset` 分页公式**：

| 参数 | 含义 | 第 1 页（每页 10 条） | 第 2 页 |
|---|---|---|---|
| `Limit` | 取几条 | 10 | 10 |
| `Offset` | 跳过几条 | 0 | 10 |

- `Offset((q.Page - 1) * q.PageSize)`：第 1 页跳过 0 条，第 2 页跳过 10 条，第 3 页跳过 20 条。

**`items := make([]models.Item, 0)` —— 别写成 `var items []models.Item`**：

```go
var items []models.Item         // 查不到数据时 → JSON 里是 "list": null
items := make([]models.Item, 0) // 查不到数据时 → JSON 里是 "list": []
```

| 前端代码 | 拿到 `[]` | 拿到 `null` |
|---|---|---|
| `data.list.map(...)` | 正常（空数组，什么都不渲染） | **报错崩溃** |

- 一个初始化方式的区别，决定"搜索无结果"时前端会不会白屏。

**`?` 占位符 —— 防 SQL 注入的生命线**：
- 假设偷懒写成字符串拼接：`"title LIKE '%" + q.Keyword + "%'"`。有人在搜索框里输入 `' OR '1'='1`，拼出来的 SQL 变成 `WHERE title LIKE '%' OR '1'='1%'` —— 条件永远成立，全表数据都被搜出来；更狠的还能拼 `'; DROP TABLE items; --` 直接删表。
- 用 `?` 占位符时，数据库**先编译 SQL 结构、再把值当纯数据填进去**，值永远不会被当成 SQL 代码执行。
- 结论：所有要进 SQL 的值，一律 `?` 占位。

**GORM 最终执行的两条 SQL**：

```sql
-- 第一次：数总数
SELECT COUNT(*) FROM items
WHERE (title LIKE '%校园卡%' OR description LIKE '%校园卡%') AND status = 'searching';

-- 第二次：取当页
SELECT * FROM items
WHERE (title LIKE '%校园卡%' OR description LIKE '%校园卡%') AND status = 'searching'
ORDER BY created_at DESC LIMIT 10 OFFSET 0;
```

### 4.2.6 第 4 步：返回

**数据变化**：`[]models.Item` + `total` → JSON → 浏览器。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [
      { "id": 4, "title": "校园卡", "status": "searching", ... },
      { "id": 3, "title": "钥匙串", "status": "searching", ... }
    ],
    "total": 3,
    "page": 1,
    "page_size": 10
  }
}
```

- 前端拿到 `total: 3` 和当前 `list` 的 2 条，就知道**还有下一页**；用户往下滑时再请求 `page=2`。
- 列表里的每条记录都**不含 `contact`** —— `json:"-"` 对数组里的每个元素同样生效（例一 4.1.10 讲过）。
- 如果搜"不存在的东西"，`list` 是 `[]`（不是 `null`），`total` 是 0，前端正常渲染"没有找到相关结果"。

# 第五章 五层架构，一层一层讲

## 5.0 总览：一次请求穿过哪几层

```
浏览器请求
   │
   ▼
router        根据「HTTP 方法 + URL」找到对应的处理函数
   │
   ▼
middleware    验 token（只有需要登录的接口才挂）
   │
   ▼
controller    收参数 → 调 service → 发响应（翻译层，不写业务逻辑）
   │
   ▼
service       业务规则：存在吗？是你的吗？能这么改吗？
   │
   ▼
dao           读写数据库（增删改查，不管业务）
   │
   ▼
MySQL
```

| 层 | 文件 | 职责 |
|---|---|---|
| router | `router/router.go` | 「方法 + URL」→ 处理函数 的映射表 |
| middleware | `middleware/auth.go` | 登录校验 |
| controller | `controller/*.go` | HTTP 世界 ↔ 业务世界的翻译 |
| service | `service/*.go` | 全部业务规则 |
| dao | `dao/*.go` | 数据库读写 |
| models | `models/*.go` | 数据结构定义（数据长什么样） |
| utils | `utils/*.go` | 通用工具（token、密码、响应格式、时间） |

调用关系是**单向**的：controller 调 service，service 调 dao，dao 调数据库。反过来不行 —— dao 不认识 service，service 不认识 HTTP。

下面按调用顺序逐层展开。每层先贴**完整代码**，再逐段说明每一行在干什么。

---

## 5.1 router（路由层）—— `router/router.go`

**职责**：把「HTTP 方法 + URL」映射到对应的处理函数。整个文件只做一件事：注册路由。

**完整代码**：

```go
package router

import (
	"net/http"

	"lostfound/controller"
	"lostfound/middleware"

	"github.com/gin-contrib/cors"
	"github.com/gin-gonic/gin"
)

// Setup 注册所有中间件和路由，返回配置好的 Gin 引擎
func Setup() *gin.Engine {
	r := gin.Default()

	// CORS（跨域）中间件：允许前端页面从别的地址调用本服务
	// 不加的话，浏览器会拦下请求（前端页面和 API 不同源是常态，联调必炸的点）
	r.Use(cors.New(cors.Config{
		AllowAllOrigins: true,
		AllowMethods:    []string{"GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"},
		AllowHeaders:    []string{"Origin", "Content-Type", "Authorization"},
	}))

	// 健康检查：用来确认服务活着
	r.GET("/ping", func(c *gin.Context) {
		c.JSON(200, gin.H{"message": "pong"})
	})

	// 托管前端页面：把 web/ 目录当作静态资源
	// 访问 http://localhost:8080/app/ 就能打开首页
	// （挂在 /app 下是为了不和 /api 路由冲突）
	r.Static("/app", "./web")

	// 访问根路径时直接跳到前端
	r.GET("/", func(c *gin.Context) {
		c.Redirect(http.StatusFound, "/app/")
	})

	// 所有业务接口统一挂在 /api 下
	api := r.Group("/api")

	// ---------- 认证模块 ----------
	auth := api.Group("/auth")
	{
		auth.POST("/register", controller.Register) // 注册
		auth.POST("/login", controller.Login)       // 登录
		auth.GET("/me", middleware.JWTAuth(), controller.GetMe)
		auth.POST("/logout", middleware.JWTAuth(), controller.Logout)
	}

	// ---------- 物品模块 ----------
	items := api.Group("/items")
	{
		items.GET("", controller.ListItems)                     // 列表（公开，支持搜索/筛选/分页）
		items.POST("", middleware.JWTAuth(), controller.CreateItem) // 发布（需登录）

		// ⚠️ /my 写在 /:id 前面：Gin 会优先匹配静态路由，但保持这个顺序更保险
		items.GET("/my", middleware.JWTAuth(), controller.MyItems) // 我的发布（需登录）

		items.GET("/:id", controller.GetItem)                                    // 详情（公开）
		items.GET("/:id/contact", middleware.JWTAuth(), controller.GetContact)   // 联系方式（需登录）
		items.PUT("/:id", middleware.JWTAuth(), controller.UpdateItem)           // 编辑（仅本人）
		items.PATCH("/:id/status", middleware.JWTAuth(), controller.UpdateStatus) // 改状态（仅本人）
		items.DELETE("/:id", middleware.JWTAuth(), controller.DeleteItem)        // 删除（仅本人）
	}

	return r
}
```

**逐段说明**：

**包声明与导入（第 1-11 行）**
- `package router`：声明本文件属于 router 包。
- 导入分三组、用空行隔开（Go 惯例）：标准库 `net/http`；本项目包 `lostfound/controller`、`lostfound/middleware`；第三方包 `cors`、`gin`。

**`Setup()` 函数签名与引擎创建（第 14-15 行）**
- `func Setup() *gin.Engine`：返回配置好的 Gin 引擎。`main.go` 里调用它拿到 `r`，再 `r.Run()` 启动。
- `gin.Default()`：创建引擎，自带两个全局中间件 —— Logger（打印访问日志）、Recovery（某个处理函数 panic 时不让整个服务崩掉）。

**CORS 中间件（第 19-23 行）**
- `r.Use(...)`：挂**全局**中间件，所有请求都要过。
- `AllowAllOrigins: true`：允许任意来源的页面调用本服务。`AllowMethods` 列出允许的 HTTP 方法，`AllowHeaders` 列出允许的请求头（`Authorization` 必须在内，否则前端带 token 的请求会被浏览器拦）。
- 为什么需要它：浏览器有同源策略，前端页面与 API 不同域名/端口时，浏览器会拦下响应。本项目前端由后端托管（同源），但开发时可能用 `file://` 或别的端口打开页面，所以保留。

**健康检查（第 26-28 行）**
- 注册一条最简单的路由：`GET /ping` 返回 `{"message":"pong"}`。用途：部署后用 `curl` 请求一下，确认服务活着。

**托管前端静态文件（第 33 行）**
- `r.Static("/app", "./web")`：把 `web/` 目录当静态资源挂在 `/app` 下。访问 `http://localhost:8080/app/` 即打开前端首页。
- 挂 `/app` 而不是根路径，是为了不和 `/api` 开头的接口路由冲突。

**根路径重定向（第 36-38 行）**
- 访问 `/` 时 302 跳到 `/app/`，用户不用手输 `/app/`。

**路由分组（第 41、44、53 行）**
- `r.Group("/api")`：建一个分组，记住前缀 `/api`。分组只是"记账"——注册路由时自动把前缀拼上，等价于每条都手写完整路径。
- `api.Group("/auth")`：嵌套分组，前缀变成 `/api/auth`。

**认证模块 4 条路由（第 46-49 行）**

| 路由 | 处理函数 | 需登录 |
|---|---|---|
| `POST /api/auth/register` | `controller.Register` | 否 |
| `POST /api/auth/login` | `controller.Login` | 否 |
| `GET /api/auth/me` | `middleware.JWTAuth()` → `controller.GetMe` | **是** |
| `POST /api/auth/logout` | `middleware.JWTAuth()` → `controller.Logout` | **是** |

- 需登录的写法：`auth.GET("/me", middleware.JWTAuth(), controller.GetMe)` —— `JWTAuth()` 写在处理函数**前面**，Gin 会先执行它，通过后才轮到 `GetMe`。这是"路由级中间件"，只作用于这一条路由。
- 注册、登录不能要登录：否则死锁（没账号就没法登录，不登录又不能注册）。

**物品模块 8 条路由（第 55-65 行）**

| 路由 | 处理函数 | 需登录 |
|---|---|---|
| `GET /api/items` | `controller.ListItems` | 否 |
| `POST /api/items` | `controller.CreateItem` | 是 |
| `GET /api/items/my` | `controller.MyItems` | 是 |
| `GET /api/items/:id` | `controller.GetItem` | 否 |
| `GET /api/items/:id/contact` | `controller.GetContact` | 是 |
| `PUT /api/items/:id` | `controller.UpdateItem` | 是 |
| `PATCH /api/items/:id/status` | `controller.UpdateStatus` | 是 |
| `DELETE /api/items/:id` | `controller.DeleteItem` | 是 |

- `:id` 是**路径参数**：`/api/items/123` 和 `/api/items/456` 都匹配 `/:id`，数字部分会被交给处理函数（用 `c.Param("id")` 取）。
- `items.GET("")` 里的空字符串表示"就是分组前缀本身"，即 `GET /api/items`。

**`/my` 和 `/:id` 的匹配规则（第 59 行注释）**
- `/api/items/my` 同时符合 `/my` 和 `/:id` 两条规则。Gin 的匹配顺序是**静态路径优先**：先找有没有字面量 `/my`，找不到才用 `:id` 兜底。所以两条能共存，`my` 不会被当成一个 id。
- 副作用：`/api/items/abc` 也会落到 `:id` 上（`abc` 被当成 id）。所以 controller 里必须校验 id 是不是合法数字 —— 见 5.3 的 `parseID`。

## 5.2 middleware（中间件层）—— `middleware/auth.go`

**职责**：在请求到达处理函数**之前**执行的一道关卡。本项目只有一个中间件：`JWTAuth`，负责"验明正身"。

**完整代码**：

```go
package middleware

import (
	"strings"

	"lostfound/utils"

	"github.com/gin-gonic/gin"
)

// JWTAuth 认证中间件：挂在需要登录的接口前面，负责"验明正身"
//
// 为什么写成 func() gin.HandlerFunc（返回函数的函数，即闭包）而不是直接写处理函数？
// 因为中间件将来可能需要参数（比如权限等级），返回函数的形式可以带参数，
// 这是 Gin 社区的标准写法（本地李文周博客里也是这个签名）
func JWTAuth() gin.HandlerFunc {
	return func(c *gin.Context) {
		// 1. 从请求头里取 Authorization，格式规定为：Bearer <token>
		authHeader := c.GetHeader("Authorization")
		if authHeader == "" {
			utils.Fail(c, utils.CodeUnauthorized, "请先登录")
			c.Abort() // ★ 关键：终止后续处理函数，不写这行的话接口还会继续执行！
			return
		}

		// 2. 按空格切成两段，校验格式（SplitN 的 2 表示最多切一刀）
		parts := strings.SplitN(authHeader, " ", 2)
		if len(parts) != 2 || parts[0] != "Bearer" {
			utils.Fail(c, utils.CodeUnauthorized, "token 格式错误，应为：Bearer xxx")
			c.Abort()
			return
		}

		// 3. 解析 token（签名对不对？过期没有？）
		claims, err := utils.ParseToken(parts[1])
		if err != nil {
			utils.Fail(c, utils.CodeUnauthorized, "登录已过期，请重新登录")
			c.Abort()
			return
		}

		// 4. 把用户信息存进本次请求的上下文，后面的处理函数用 c.GetUint("user_id") 取
		//    （Context 相当于"这次请求的随身口袋"，中间件放进去，handler 拿出来）
		c.Set("user_id", claims.UserID)
		c.Set("username", claims.Username)

		c.Next() // 放行，交给下一个处理函数
	}
}
```

**逐段说明**：

**函数签名（第 16 行）**
- `func JWTAuth() gin.HandlerFunc`：**返回函数的函数**。调用 `JWTAuth()` 得到真正的中间件函数，交给 Gin 执行。
- 为什么包一层？为了将来能带参数（比如 `JWTAuth("admin")` 限定管理员才能过）。这是 Gin 中间件的标准写法。
- `gin.HandlerFunc` 就是 `func(*gin.Context)` 的类型别名 —— 中间件和处理函数本质是同一种东西，都是"接收 Context 的函数"。

**第 1 步：取 token（第 19-24 行）**
- `c.GetHeader("Authorization")`：从请求头取 `Authorization` 字段，约定格式为 `Bearer <token>`（Bearer = 持有者，HTTP 认证的标准写法）。
- 取不到（空字符串）→ `utils.Fail` 返回 401「请先登录」。
- `c.Abort()` 是关键：**不调用它的话，中间件返回后 Gin 还会继续执行后面的处理函数**，等于没拦住。所以每个失败分支都是三件套：发错误响应 → `c.Abort()` → `return`。

**第 2 步：校验格式（第 27-32 行）**
- `strings.SplitN(authHeader, " ", 2)`：按空格切一刀，最多切成 2 段。`"Bearer abc.def.ghi"` → `["Bearer", "abc.def.ghi"]`。
- 校验两件事：切出来必须是 2 段（`len(parts) != 2`），且第一段必须是 `Bearer`。
- 用 `SplitN` 而不是 `Split`：最多切一刀，第二段保留剩余全部内容，不会把 token 切碎。

**第 3 步：验签（第 35-40 行）**
- `utils.ParseToken(parts[1])`：解析并校验 token —— 签名对不对（有没有被篡改）、过期没有。实现见 5.7。
- 失败 → 401「登录已过期，请重新登录」。两种情况（篡改、过期）合并成同一句提示，不向前端区分具体原因。

**第 4 步：把身份放进 Context（第 44-45 行）**
- `c.Set("user_id", claims.UserID)`：把 token 里解析出的用户 ID 存进本次请求的 Context。
- Context 是"这次请求的随身口袋"：中间件放进去，后续处理函数用 `c.GetUint("user_id")` 取出。
- 关键：`user_id` 来自 **token 里的签名内容**，不是前端传的字段。这是"身份不可伪造"的根基 —— 详见 5.4 的说明。

**第 5 步：放行（第 47 行）**
- `c.Next()`：交给下一个函数（真正的处理函数）。
- 其实中间件里什么都不写也会继续往下走，`c.Next()` 写出来是为了意图明确：这里是"通过"的分支。

## 5.3 controller（控制器层）—— `controller/*.go`

**职责**：**翻译层**。把 HTTP 世界的东西（JSON 文本、URL 参数、请求头）翻译成业务层认识的 Go 值，再把业务层的结果翻译回 HTTP 响应（状态码 + JSON）。

controller **不写任何业务逻辑**。每个处理函数都是同一个骨架：

```
收参数（+ 校验格式） → 调 service → 判错误 → 发响应
```

两个文件：`item_controller.go`（8 个物品接口）、`user_controller.go`（4 个认证接口）。

### 5.3.1 `controller/item_controller.go`

**完整代码**：

```go
package controller

import (
	"errors"
	"strconv"

	"lostfound/models"
	"lostfound/service"
	"lostfound/utils"

	"github.com/gin-gonic/gin"
)

// parseID 从 URL 里取出 :id 并转成 uint
// 必须校验：/api/items/abc 会落到 :id 路由上，不校验的话会把脏字符串传给数据库
func parseID(c *gin.Context) (uint, bool) {
	id, err := strconv.ParseUint(c.Param("id"), 10, 64)
	if err != nil || id == 0 {
		utils.Fail(c, utils.CodeInvalidParam, "id 不合法")
		return 0, false
	}
	return uint(id), true
}

// parsePagination 解析分页参数，带默认值和上限保护（防止有人传 page_size=999999）
func parsePagination(c *gin.Context) (int, int) {
	page, _ := strconv.Atoi(c.DefaultQuery("page", "1"))
	pageSize, _ := strconv.Atoi(c.DefaultQuery("page_size", "10"))
	if page < 1 {
		page = 1
	}
	if pageSize < 1 || pageSize > 50 {
		pageSize = 10
	}
	return page, pageSize
}

// handleItemError 把 service 层的业务错误统一翻译成响应
// （集中在一处，避免每个接口都写一遍 if-else）
func handleItemError(c *gin.Context, err error) {
	switch {
	case errors.Is(err, service.ErrItemNotFound):
		utils.Fail(c, utils.CodeNotFound, err.Error())
	case errors.Is(err, service.ErrNotOwner):
		utils.Fail(c, utils.CodeForbidden, err.Error())
	case errors.Is(err, service.ErrStatusBackward):
		utils.Fail(c, utils.CodeStatusBackward, err.Error())
	case errors.Is(err, service.ErrBadTime):
		utils.Fail(c, utils.CodeInvalidParam, err.Error())
	default:
		utils.Fail(c, utils.CodeServerError, "服务器开小差了")
	}
}

// ListItems 处理 GET /api/items —— 公开列表（搜索 / 筛选 / 分页）
func ListItems(c *gin.Context) {
	page, pageSize := parsePagination(c)

	// 状态默认只看"寻找中"（PRD 4.3：首页默认展示寻找中的信息）
	// 传 status=all 或 status=（空）表示不限状态
	status := c.DefaultQuery("status", string(models.StatusSearching))
	if status == "all" {
		status = ""
	}

	items, total, err := service.ListItems(models.ItemListQuery{
		Keyword:  c.Query("keyword"),  // 关键词模糊搜索
		Type:     c.Query("type"),     // lost / found
		Category: c.Query("category"), // card / electronics / ...
		Campus:   c.Query("campus"),
		Place:    c.Query("place"),
		Status:   status,
		Page:     page,
		PageSize: pageSize,
	})
	if err != nil {
		utils.Fail(c, utils.CodeServerError, "查询失败")
		return
	}

	// 返回 total 供前端判断"还有没有下一页"（上拉加载更多）
	utils.OK(c, gin.H{
		"list":      items,
		"total":     total,
		"page":      page,
		"page_size": pageSize,
	})
}

// MyItems 处理 GET /api/items/my —— 我的发布（含全部状态，需登录）
func MyItems(c *gin.Context) {
	page, pageSize := parsePagination(c)
	userID := c.GetUint("user_id")

	items, total, err := service.ListItems(models.ItemListQuery{
		UserID:   userID,
		Status:   "", // 我的发布：所有状态都列出来，方便管理
		Page:     page,
		PageSize: pageSize,
	})
	if err != nil {
		utils.Fail(c, utils.CodeServerError, "查询失败")
		return
	}

	utils.OK(c, gin.H{
		"list":      items,
		"total":     total,
		"page":      page,
		"page_size": pageSize,
	})
}

// GetItem 处理 GET /api/items/:id —— 详情（公开，但不含联系方式）
func GetItem(c *gin.Context) {
	id, ok := parseID(c)
	if !ok {
		return
	}

	detail, err := service.GetItemDetail(id)
	if err != nil {
		handleItemError(c, err)
		return
	}
	utils.OK(c, detail)
}

// GetContact 处理 GET /api/items/:id/contact —— 查看联系方式（需登录）
func GetContact(c *gin.Context) {
	id, ok := parseID(c)
	if !ok {
		return
	}

	contact, err := service.GetContact(id)
	if err != nil {
		handleItemError(c, err)
		return
	}
	utils.OK(c, gin.H{"contact": contact})
}

// CreateItem 处理 POST /api/items —— 发布（需登录）
func CreateItem(c *gin.Context) {
	var req models.CreateItemRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	userID := c.GetUint("user_id")
	item, err := service.CreateItem(userID, req)
	if err != nil {
		handleItemError(c, err)
		return
	}
	utils.OKMsg(c, "发布成功", item)
}

// UpdateItem 处理 PUT /api/items/:id —— 编辑（仅本人）
func UpdateItem(c *gin.Context) {
	id, ok := parseID(c)
	if !ok {
		return
	}

	var req models.UpdateItemRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	userID := c.GetUint("user_id")
	item, err := service.UpdateItem(userID, id, req)
	if err != nil {
		handleItemError(c, err)
		return
	}
	utils.OKMsg(c, "修改成功", item)
}

// UpdateStatus 处理 PATCH /api/items/:id/status —— 改状态（仅本人，只能前进）
func UpdateStatus(c *gin.Context) {
	id, ok := parseID(c)
	if !ok {
		return
	}

	var req models.UpdateStatusRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	userID := c.GetUint("user_id")
	if err := service.UpdateStatus(userID, id, req.Status); err != nil {
		handleItemError(c, err)
		return
	}
	utils.OKMsg(c, "状态已更新", nil)
}

// DeleteItem 处理 DELETE /api/items/:id —— 删除（仅本人）
func DeleteItem(c *gin.Context) {
	id, ok := parseID(c)
	if !ok {
		return
	}

	userID := c.GetUint("user_id")
	if err := service.DeleteItem(userID, id); err != nil {
		handleItemError(c, err)
		return
	}
	utils.OKMsg(c, "删除成功", nil)
}
```

**逐段说明**：

**`parseID()`（第 16-23 行）—— 解析并校验路径参数 `:id`**
- `c.Param("id")`：取出 URL 里的 `:id` 部分，**是字符串**（比如 `"123"`）。
- `strconv.ParseUint(..., 10, 64)`：按十进制转成 64 位无符号整数。失败（比如 `/api/items/abc`）返回 err。
- `if err != nil || id == 0`：转换失败或 id 为 0 都算不合法（0 不是合法主键）。此时直接发 400 响应，返回 `false` 告诉调用方"已经处理过了，直接 return 就行"。
- 返回 `(uint, bool)` 两个值：调用方用 `id, ok := parseID(c); if !ok { return }` 的固定模式使用。
- 这个函数是必需的：路由 `/api/items/:id` 会匹配任何字符串，不校验的话脏数据会一路传到数据库。

**`parsePagination()`（第 26-36 行）—— 解析分页参数**
- `c.DefaultQuery("page", "1")`：取 URL 问号后的 `page` 参数，没传就用默认值 `"1"`（返回字符串）。
- `strconv.Atoi(...)`：字符串转 int。`_` 忽略错误 —— 传了非数字就当默认值处理（下面 `page < 1` 会兜住）。
- 两道保护：`page < 1` 归 1；`pageSize` 不在 1~50 范围内归 10。**上限 50 是防止有人传 `page_size=999999` 一次性拉全表**。

**`handleItemError()`（第 40-53 行）—— 业务错误 → HTTP 响应的翻译器**
- 入参是 service 层返回的 error，用 `errors.Is` 判断是哪种业务错误，翻译成对应的错误码：

| service 返回 | 翻译成 | 含义 |
|---|---|---|
| `ErrItemNotFound` | 404 | 帖子不存在 |
| `ErrNotOwner` | 403 | 存在，但不是你发的 |
| `ErrStatusBackward` | 400 | 状态想回退/原地/非法值 |
| `ErrBadTime` | 400 | 时间格式不对 |
| 其他（default） | 500 | 没预料到的错误 |

- `default` 分支**不透传 `err.Error()`**，固定返回「服务器开小差了」：未知错误可能是数据库报错，细节（表名、SQL）不该暴露给前端。
- 集中写在一个函数里的意义：8 个接口共用这一份映射，加一种新错误只改这一处。

**`ListItems()`（第 56-88 行）—— 公开列表**
- 第 57 行：`parsePagination` 拿分页参数。
- 第 61-64 行：`status` 默认值取 `"searching"`（首页默认只看"寻找中"）；传 `status=all` 时置空字符串，表示"不限状态"（dao 里空字符串会跳过状态过滤）。
- 第 66-75 行：把 URL 上所有筛选条件收集成 `models.ItemListQuery` 结构体，一次交给 service。注意 `Keyword`/`Type`/`Category` 等直接来自 `c.Query(...)`，没传就是空字符串，dao 里会跳过对应的过滤条件。
- 第 76-79 行：service 返回错误 → 500。列表接口的失败基本都是数据库问题，没有需要区分细分的业务错误。
- 第 82-87 行：`utils.OK` 发响应。`gin.H` 是 `map[string]any` 的简写。返回 `total` 是给前端判断"还有没有下一页"用的。

**`MyItems()`（第 91-112 行）—— 我的发布**
- 和 `ListItems` 几乎一样，两处不同：
  - `userID := c.GetUint("user_id")`：从 Context 取当前用户（中间件放的），**不是**从 URL 参数取 —— 所以"我的发布"伪造不了。
  - `Status: ""`：我的发布不限状态（寻找中/已找到/已结束都要能看到，方便管理）。

**`GetItem()`（第 115-127 行）—— 详情**
- `id, ok := parseID(c)`：标准解析模式，失败直接 return（`parseID` 内部已发响应）。
- `service.GetItemDetail(id)` 返回的是 `ItemDetailResponse`（帖子 + 发布者昵称/学号），直接 `utils.OK` 返回。
- 出错走 `handleItemError` 翻译（可能是 404）。

**`GetContact()`（第 130-142 行）—— 查看联系方式**
- 登录校验由路由上的 `middleware.JWTAuth()` 把关，controller 里不需要再判断。
- 返回 `gin.H{"contact": contact}`：单独包一层对象。如果直接返回字符串，`data` 字段会是一个裸字符串，前端取值不方便。

**`CreateItem()`（第 145-159 行）—— 发布**
- 第 146-150 行：`c.ShouldBindJSON(&req)` 把请求体 JSON 解析进 `CreateItemRequest`，**同时执行 `binding` 校验**（必填、长度、枚举值）。校验失败返回 400，错误信息里带上具体哪个字段不合格。
- 第 152 行：`userID := c.GetUint("user_id")` —— 发布者身份**只从 token 来**。请求体里没有 `user_id` 字段（`CreateItemRequest` 里根本没定义），想冒充也没入口。
- 第 153 行：`service.CreateItem(userID, req)` —— 注意参数分两个：**可信的** `userID`（token 来的）和**不可信的** `req`（前端传的）。
- 第 158 行：成功返回 200 + "发布成功" + 新帖子数据。

**`UpdateItem()`（第 162-181 行）—— 编辑**
- 骨架同上，多了个 `:id` 解析。`userID` 和 `id` 一起传给 service，由 service 判断"是不是本人"（403 从这里出）。

**`UpdateStatus()`（第 184-202 行）—— 改状态**
- 请求体 `UpdateStatusRequest` 只有一个字段 `status`，`binding` 限制取值只能是 `searching/resolved/closed` 三个之一 —— 非法值在绑定阶段就被拦下。
- service 返回的错误可能是 404（帖子不在）、403（不是本人）、400（状态想回退），都由 `handleItemError` 翻译。
- 成功返回的 `data` 是 `nil`：改状态不需要返回新数据。

**`DeleteItem()`（第 205-217 行）—— 删除**
- 最简单的接口：解析 id → 取 userID → 调 service → 发响应。同样可能返回 404/403。

### 5.3.2 `controller/user_controller.go`

**完整代码**：

```go
package controller

import (
	"errors"

	"lostfound/models"
	"lostfound/service"
	"lostfound/utils"

	"github.com/gin-gonic/gin"
)

// Register 处理 POST /api/auth/register
func Register(c *gin.Context) {
	// 1. 解析并校验请求体：binding tag 不满足时 ShouldBindJSON 会返回 error
	var req models.RegisterRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	// 2. 交给 service 处理业务（controller 只做"收参数 → 调 service → 发响应"，不写业务逻辑）
	user, err := service.Register(req)
	if err != nil {
		if errors.Is(err, service.ErrUsernameTaken) {
			utils.Fail(c, utils.CodeUsernameTaken, err.Error())
			return
		}
		utils.Fail(c, utils.CodeServerError, "注册失败")
		return
	}

	// 3. 返回用户信息（Password 字段有 json:"-"，不会泄露）
	utils.OKMsg(c, "注册成功", user)
}

// Login 处理 POST /api/auth/login
func Login(c *gin.Context) {
	var req models.LoginRequest
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.Fail(c, utils.CodeInvalidParam, "参数错误："+err.Error())
		return
	}

	user, token, err := service.Login(req)
	if err != nil {
		if errors.Is(err, service.ErrWrongCredentials) {
			utils.Fail(c, utils.CodeWrongPassword, err.Error())
			return
		}
		utils.Fail(c, utils.CodeServerError, "登录失败")
		return
	}

	utils.OKMsg(c, "登录成功", gin.H{
		"token": token,
		"user":  user,
	})
}

// GetMe 处理 GET /api/auth/me —— 获取当前登录用户（前端用来判断"我是谁"）
func GetMe(c *gin.Context) {
	// user_id 是 JWTAuth 中间件解析 token 后塞进 Context 的
	userID := c.GetUint("user_id")

	user, err := service.GetUserByID(userID)
	if err != nil {
		utils.Fail(c, utils.CodeServerError, "获取用户信息失败")
		return
	}
	utils.OK(c, user)
}

// Logout 处理 POST /api/auth/logout
//
// 这里有个必须讲清楚的设计点：JWT 是"无状态"的 —— token 一旦签发，
// 服务端就没有它的记录，也就无法单方面作废它（除非引入 Redis 黑名单，超出本项目范围）。
// 所以"退出登录"真正发生的地方是前端：把本地保存的 token 删掉。
// 保留这个接口的意义：① 满足任务书"退出登录"的要求；② 前端有一个统一的收尾调用点，
// 将来若要换成 Redis 黑名单方案，前端代码不用改。
func Logout(c *gin.Context) {
	utils.OKMsg(c, "已退出登录（前端请删除本地保存的 token）", nil)
}
```

**逐段说明**：

**`Register()`（第 14-35 行）**
- 第 16-20 行：`ShouldBindJSON` 解析 + 校验（`RegisterRequest` 的规则：用户名 3-20 位、密码 6-32 位、都必填）。校验失败 400。
- 第 23 行：`service.Register(req)` 返回 `(user, err)` 两个值。
- 第 24-31 行：错误处理比物品接口简单 —— 只有一种业务错误 `ErrUsernameTaken`（用户名已被注册，1005），其余归 500。注意这里**没有**用 `handleItemError`（那是物品模块的翻译器），是就地判断。
- 第 34 行：返回 user 对象。安全点：`models.User` 的 `Password` 字段带 `json:"-"`，序列化时自动剔除，**不可能**把密码哈希返回给前端。

**`Login()`（第 38-59 行）**
- 第 45 行：`service.Login(req)` 返回三个值：`user, token, err` —— 登录成功要同时给"用户信息"和"新签发的 token"。
- 第 46-52 行：`ErrWrongCredentials`（用户名或密码错误）→ 1006。service 里故意把"用户不存在"和"密码错误"合并成同一个错误 —— 不让人用这个接口探测哪些用户名已注册。
- 第 55-58 行：返回 `{token, user}` 对象。前端拿到 token 后存起来，之后每个请求放在 `Authorization` 头里。

**`GetMe()`（第 62-72 行）**
- 第 64 行：`c.GetUint("user_id")` 取当前用户 —— 能执行到这里说明中间件已经验过 token 了。
- 用途：前端刷新页面后，用本地存的 token 调一次 `/me`，就能知道"我是谁"、要不要显示登录状态。
- 第 66-70 行：这里没区分 404 —— 理论上 token 合法但用户被删了才可能查不到，属于极端情况，统一 500。

**`Logout()`（第 75-83 行）**
- 函数体只有一行：返回"已退出登录"。**什么都没做**是设计如此，不是偷懒。
- 原因：JWT 是无状态的 —— 服务端不留 token 记录，也就无法"作废"某个 token。真正的退出 = 前端删掉本地存的 token（之后请求不再带它）。
- 保留接口的两个理由：① 任务书要求有"退出登录"功能；② 给前端一个统一的调用点，将来如果升级成 Redis 黑名单方案（服务端真的作废 token），前端代码不用改。
- 这段设计说明写在函数注释里（第 76-80 行），面试被问"退出登录怎么实现的"可以直接引用。

## 5.4 service（业务层）—— `service/*.go`

**职责**：**整个后端唯一"懂业务"的地方**。所有规则判断都在这里：

1. **校验与权限**：这条数据存在吗？是你发的吗？能这么改吗？
2. **加工数据**：时间字符串转 `time.Time`、密码加密、组装新结构体
3. **编排流程**：先查帖子、再查发布者、最后拼成响应

service 不认识 HTTP（不知道状态码、JSON、请求头），只认 Go 的值和错误。

### 5.4.1 `service/errors.go`

**完整代码**：

```go
package service

import "errors"

// 业务错误（"哨兵错误"）：service 层把各种异常情况归纳成这几个固定错误值
// controller 用 errors.Is(err, service.ErrXxx) 判断类型，再翻译成对应的错误码
// 这是 Go 的风格：错误是"值"，用比较来判断，而不是像其他语言的 try/catch
var (
	ErrUsernameTaken    = errors.New("用户名已被注册")
	ErrWrongCredentials = errors.New("用户名或密码错误")
	ErrItemNotFound     = errors.New("信息不存在")
	ErrNotOwner         = errors.New("只能操作自己发布的信息")
	ErrStatusBackward   = errors.New("状态只能前进，不能回退")
	ErrBadTime          = errors.New("时间格式不正确")
)
```

**逐段说明**：
- 六个 `var` 是**哨兵错误**：预先定义好的、代表特定业务情况的错误值。Go 没有 try/catch，错误的传递方式是"函数返回 error 值"，判断方式是用 `errors.Is(err, service.ErrXxx)` 比较。
- 每个错误的文案会**原样返回给前端**（controller 里 `err.Error()` 拿的就是这里的字符串）—— 所以文案要写成用户能看懂的话，不是给程序员看的调试信息。
- 集中定义的意义：所有业务错误在一处可查。想加一种新错误（比如"帖子已关闭不能编辑"），在这里加一行，controller 的翻译器加一个 case。

### 5.4.2 `service/item_service.go`

**完整代码**：

```go
package service

import (
	"errors"

	"lostfound/dao"
	"lostfound/models"
	"lostfound/utils"
)

// statusOrder 状态顺序表：数字越大越靠后，用来判断"是不是在前进"
// 把状态机的规则集中在这一张表里，改规则只改这里
var statusOrder = map[models.ItemStatus]int{
	models.StatusSearching: 0,
	models.StatusResolved:  1,
	models.StatusClosed:    2,
}

// CreateItem 发布：解析时间 → 组装 → 入库
func CreateItem(userID uint, req models.CreateItemRequest) (*models.Item, error) {
	happenedAt, err := utils.ParseTime(req.HappenedAt)
	if err != nil {
		return nil, ErrBadTime
	}

	item := &models.Item{
		Type:        req.Type,
		Title:       req.Title,
		Category:    models.ItemCategory(req.Category),
		Campus:      req.Campus,
		Place:       req.Place,
		HappenedAt:  happenedAt,
		Description: req.Description,
		Contact:     req.Contact,
		Status:      models.StatusSearching, // 新帖一律从"寻找中"开始
		UserID:      userID,
	}
	if err := dao.CreateItem(item); err != nil {
		return nil, err
	}
	return item, nil
}

// GetItemDetail 详情：帖子 + 发布者昵称/学号（PRD 5.2 详情页要显示）
func GetItemDetail(id uint) (*models.ItemDetailResponse, error) {
	item, err := dao.GetItemByID(id)
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			return nil, ErrItemNotFound
		}
		return nil, err
	}

	// 再查一次发布者（只在详情接口查，列表接口不查 —— 避免"每行都查一次用户"的 N+1 问题）
	publisher, err := dao.GetUserByID(item.UserID)
	if err != nil {
		return nil, err
	}

	return &models.ItemDetailResponse{
		Item:               *item,
		PublisherNickname:  publisher.Nickname,
		PublisherStudentID: publisher.StudentID,
	}, nil
}

// GetContact 查看联系方式（登录由路由中间件把关，service 只管取数据）
func GetContact(itemID uint) (string, error) {
	item, err := dao.GetItemByID(itemID)
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			return "", ErrItemNotFound
		}
		return "", err
	}
	return item.Contact, nil
}

// ListItems 列表查询（条件筛选、分页都在 dao 里实现）
func ListItems(q models.ItemListQuery) ([]models.Item, int64, error) {
	return dao.ListItems(q)
}

// UpdateItem 编辑：先确认帖子存在、且是本人发的
func UpdateItem(userID, itemID uint, req models.UpdateItemRequest) (*models.Item, error) {
	item, err := dao.GetItemByID(itemID)
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			return nil, ErrItemNotFound
		}
		return nil, err
	}
	if item.UserID != userID {
		return nil, ErrNotOwner // 存在但不是你的 → 403（区别于"不存在"的 404）
	}

	// 只更新"传了的"字段（空字符串视为不修改）
	fields := map[string]any{}
	if req.Title != "" {
		fields["title"] = req.Title
	}
	if req.Category != "" {
		fields["category"] = req.Category
	}
	if req.Campus != "" {
		fields["campus"] = req.Campus
	}
	if req.Place != "" {
		fields["place"] = req.Place
	}
	if req.HappenedAt != "" {
		t, err := utils.ParseTime(req.HappenedAt)
		if err != nil {
			return nil, ErrBadTime
		}
		fields["happened_at"] = t
	}
	if req.Description != "" {
		fields["description"] = req.Description
	}
	if req.Contact != "" {
		fields["contact"] = req.Contact
	}

	if len(fields) > 0 {
		if err := dao.UpdateItemFields(itemID, fields); err != nil {
			return nil, err
		}
	}

	// 返回更新后的最新数据
	return dao.GetItemByID(itemID)
}

// UpdateStatus 改状态：仅本人 + 只能前进（寻找中 → 已找到 → 已结束）
// 注意：编辑接口（UpdateItem）故意不开放 status 字段，否则状态机形同虚设
func UpdateStatus(userID, itemID uint, newStatus models.ItemStatus) error {
	item, err := dao.GetItemByID(itemID)
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			return ErrItemNotFound
		}
		return err
	}
	if item.UserID != userID {
		return ErrNotOwner
	}

	// 只能前进：新状态的序号必须严格大于当前状态（相等=原地不动，小于=回退，都不允许）
	if statusOrder[newStatus] <= statusOrder[item.Status] {
		return ErrStatusBackward
	}

	return dao.UpdateItemFields(itemID, map[string]any{"status": newStatus})
}

// DeleteItem 删除：仅本人
func DeleteItem(userID, itemID uint) error {
	item, err := dao.GetItemByID(itemID)
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			return ErrItemNotFound
		}
		return err
	}
	if item.UserID != userID {
		return ErrNotOwner
	}
	return dao.DeleteItem(itemID)
}
```

**逐段说明**：

**`statusOrder` 状态顺序表（第 13-17 行）**
- 把三个状态映射成数字：寻找中 0 < 已找到 1 < 已结束 2。"能前进" = 新状态数字**严格大于**当前状态。
- 这是"把规则抽成数据"的写法：判断逻辑只需要一个 `<=`（见 `UpdateStatus`），加第四个状态（比如"已过期"）时只往这张表加一行，判断代码一个字不用改。
- 对比笨办法：`if 旧状态 == A && 新状态 == B || 旧状态 == B && 新状态 == C ...` —— 三个状态要枚举 6 种组合，四个状态 12 种。

**`CreateItem()`（第 20-42 行）—— 发布**
- 第 21-24 行：`utils.ParseTime` 把前端传来的时间**字符串**解析成 `time.Time`。解析失败返回 `ErrBadTime`（→ 400）。用字符串收时间的原因见 5.7。
- 第 26-37 行：逐字段组装 `models.Item`。**两个字段不是从 req 抄的**：
  - `Status: models.StatusSearching`：新帖一律"寻找中"，**不看前端传什么**（`CreateItemRequest` 里也没有这个字段）。
  - `UserID: userID`：来自函数参数（= token 里的用户），**不是** req 里的。
  - 这两个"写死"是安全设计：状态和归属权如果由前端决定，别人就能伪造。
- 第 38-40 行：调 dao 入库。GORM 会把结构体转成 INSERT，并回填自增 ID（`item.ID` 入库后才有值）。
- 第 41 行：返回入库后的 item（带 ID、创建时间），controller 直接拿去响应。

**`GetItemDetail()`（第 45-65 行）—— 详情（编排）**
- 第 46-52 行：先查帖子。**错误翻译**：dao 的 `ErrNotFound` 翻成 `ErrItemNotFound`（给 controller 判 404 用）；其他错误原样上抛（那是数据库真出问题，会变成 500）。
- 第 55-58 行：再查发布者。详情页要显示"发布者昵称 + 学号"，这些在 users 表里，得第二次查询。
- 第 60-64 行：组装 `ItemDetailResponse`（帖子 + 发布者两个字段）。`*item` 解引用把 Item 的值拷进去。
- **这是 service"编排"职责的典型**：dao 只会"查一张表"，"把两张表的数据拼起来"是 service 的事。
- 注意只有详情这么干，列表不查发布者：列表一次返回 10 条，每条都查用户就是 11 次查询（N+1 问题），而且列表页也不显示昵称。

**`GetContact()`（第 68-77 行）—— 取联系方式**
- 唯一的业务逻辑是错误翻译（不存在 → `ErrItemNotFound`）。"必须登录"由路由中间件保证，service 不重复判断。
- 返回 `item.Contact`：这个字段在 `Item` 结构体上是 `json:"-"`，正常途径（列表/详情）永远输出不了它，只有这个函数显式返回才拿得到。

**`ListItems()`（第 80-82 行）—— 列表**
- 纯转发：把查询条件原样交给 dao。列表没有业务规则（筛选、分页都是 SQL 层面的事），所以 service 这层只是"保持分层完整"。
- 保留这一层的意义：将来加规则（比如"已结束的帖子超过 30 天不显示"）就有地方放了，controller 不用改。

**`UpdateItem()`（第 85-133 行）—— 编辑**
- 第 86-95 行：**"存在 → 归属"两段检查**，顺序不能反：
  - 先查存在：不存在 → `ErrItemNotFound`（404）。此时 `item` 是 nil，直接 return。
  - 再查归属：`item.UserID != userID` → `ErrNotOwner`（403）。
  - 404 和 403 必须分开：东西不存在和"东西在但归别人"对前端是两种提示。
- 第 98-123 行：**"传了就改，没传就不动"** —— 每个字段判断 `!= ""`，非空才放进 `fields` map。这就是编辑接口"部分更新"的实现。
- 第 111-117 行：时间字段特殊处理：传了才解析，解析失败返回 `ErrBadTime`。
- 第 125-129 行：`fields` 非空才执行 UPDATE（全都没传就不必碰数据库）。
- 第 132 行：**返回更新后的最新数据**（重新查一次），而不是把请求里的值拼回去 —— 保证返回的 `updated_at` 等字段是数据库里的真实值。
- 注意 `UpdateItemRequest` 里**没有 status 和 type 字段**：状态只能走 `UpdateStatus`（否则状态机形同虚设），类型不可改（失物帖不该变成招领帖）。

**`UpdateStatus()`（第 137-155 行）—— 改状态**
- 第 138-147 行：同样的"存在 → 归属"检查。
- 第 150-152 行：**状态机核心**。`statusOrder[newStatus] <= statusOrder[item.Status]` 一行判断，同时挡住三种非法操作：

| 操作 | 数字比较 | 结果 |
|---|---|---|
| 寻找中 → 已找到 | 1 > 0 | 放行 |
| 寻找中 → 已结束（跳级） | 2 > 0 | 放行（跳级也算前进） |
| 已找到 → 寻找中（回退） | 0 <= 1 | 拦住 |
| 已找到 → 已找到（原地） | 1 <= 1 | 拦住 |
| 已结束 → 任何 | x <= 2 | 拦住 |

- 第 154 行：执行 UPDATE，只改 status 一个字段。

**`DeleteItem()`（第 158-170 行）—— 删除**
- "存在 → 归属"检查后直接 `dao.DeleteItem`。删除没有额外的业务规则（不像状态有状态机），所以最短。

### 5.4.3 `service/user_service.go`

**完整代码**：

```go
package service

import (
	"errors"
	"strings"

	"lostfound/dao"
	"lostfound/models"
	"lostfound/utils"
)

// Register 注册：查重 → 密码加密 → 入库
func Register(req models.RegisterRequest) (*models.User, error) {
	// 1. 先查用户名有没有被占用（主动查一次，比等数据库报唯一索引冲突再翻译更友好）
	_, err := dao.GetUserByUsername(req.Username)
	if err == nil {
		return nil, ErrUsernameTaken // 查到了 → 用户名已存在
	}
	if !errors.Is(err, dao.ErrNotFound) {
		return nil, err // 不是"没找到"，而是数据库真出错了
	}

	// 2. 密码加密（绝不能明文存库；bcrypt 自带随机盐）
	hash, err := utils.HashPassword(req.Password)
	if err != nil {
		return nil, err
	}

	// 3. 组装成 User 并入库（TrimSpace 去掉首尾空格，防止" admin"这种绕过查重）
	user := &models.User{
		Username:  strings.TrimSpace(req.Username),
		Password:  hash,
		Nickname:  strings.TrimSpace(req.Nickname),
		StudentID: strings.TrimSpace(req.StudentID),
	}
	if err := dao.CreateUser(user); err != nil {
		return nil, err
	}
	return user, nil
}

// Login 登录：查用户 → 验密码 → 签发 token
func Login(req models.LoginRequest) (*models.User, string, error) {
	user, err := dao.GetUserByUsername(strings.TrimSpace(req.Username))
	if err != nil {
		if errors.Is(err, dao.ErrNotFound) {
			// 故意不区分"用户不存在"和"密码错误"：防止别人拿这个接口探测哪些用户名已注册
			return nil, "", ErrWrongCredentials
		}
		return nil, "", err
	}

	if !utils.CheckPassword(req.Password, user.Password) {
		return nil, "", ErrWrongCredentials
	}

	token, err := utils.GenToken(user.ID, user.Username)
	if err != nil {
		return nil, "", err
	}
	return user, token, nil
}

// GetUserByID 获取当前用户信息（供 /api/auth/me 用）
func GetUserByID(id uint) (*models.User, error) {
	return dao.GetUserByID(id)
}
```

**逐段说明**：

**`Register()`（第 13-40 行）—— 注册三步**
- 第 15-21 行（查重）：`dao.GetUserByUsername` 主动查一次。三种结果：
  - 查到了（`err == nil`）→ 用户名已存在，返回 `ErrUsernameTaken`。
  - 没查到（`errors.Is(err, dao.ErrNotFound)`）→ 正常，继续往下。
  - 其他错误 → 数据库真出问题了，原样上抛（→ 500）。
  - 为什么主动查而不等数据库唯一索引报错：数据库报的错要再翻译一次，不如主动查来得直接。
- 第 24-27 行（加密）：`utils.HashPassword` 用 bcrypt 加密。**数据库里存的永远是哈希值，不是明文**（详见 5.7）。
- 第 30-38 行（组装入库）：所有文本字段先 `strings.TrimSpace` 去首尾空格 —— 防的是"` admin`"这种前面带空格的用户名绕过查重。
  - 注意存的 `Password` 是 `hash`（哈希值），不是 `req.Password`（明文）。

**`Login()`（第 43-62 行）—— 登录三步**
- 第 44-51 行：按用户名查用户。查不到 → 返回 `ErrWrongCredentials`（**和密码错误用同一个错误**）。
  - 为什么不区分：如果"用户不存在"和"密码错误"返回不同提示，别人就能用这个接口逐个试用户名，探测哪些账号存在。合并成一句"用户名或密码错误"，什么信息都不给。
- 第 53-55 行：`utils.CheckPassword(req.Password, user.Password)` 把明文和数据库里的哈希比对（bcrypt 内部会从哈希里取盐重算）。不匹配 → 同样 `ErrWrongCredentials`。
- 第 57-60 行：`utils.GenToken(user.ID, user.Username)` 签发 token（把用户 ID 和用户名写进载荷，用密钥签名）。
- 第 61 行：返回三个值 —— `user`（前端显示用）、`token`（前端存起来）、`nil`（无错误）。

**`GetUserByID()`（第 65-67 行）**
- 纯转发给 dao。保留这一层是为了分层完整（controller 不直接碰 dao）。

## 5.5 dao（数据访问层）—— `dao/*.go`

**职责**：**只管跟数据库打交道** —— 增、删、改、查。不判断业务规则（那是 service 的事），不关心 HTTP（那是 controller 的事）。

三个文件：`dao.go`（公共部分）、`item_dao.go`（items 表）、`user_dao.go`（users 表）。

### 5.5.1 `dao/dao.go`

**完整代码**：

```go
package dao

import (
	"errors"

	"gorm.io/gorm"
)

// DB 是全局数据库句柄，由 main 启动时通过 InitDB 注入
// （小项目常见的简化写法：全项目共用一个连接池）
var DB *gorm.DB

// ErrNotFound 统一的"记录不存在"错误
// dao 层负责把 GORM 的 ErrRecordNotFound 翻译成它，这样上层就不用 import gorm 了
var ErrNotFound = errors.New("记录不存在")

// InitDB 注入数据库句柄（main 里调用一次）
func InitDB(db *gorm.DB) {
	DB = db
}

// translate 把 GORM 的"找不到记录"翻译成 dao.ErrNotFound，其他错误原样返回
func translate(err error) error {
	if errors.Is(err, gorm.ErrRecordNotFound) {
		return ErrNotFound
	}
	return err
}
```

**逐段说明**：

**`DB` 全局句柄（第 11 行）**
- `var DB *gorm.DB`：包级变量，存数据库连接。`main.go` 启动时通过 `InitDB` 注入一次，之后全项目的 dao 函数共用它。
- 这是小项目的简化写法（全局单例）。大项目会用依赖注入，把 DB 传进每个需要的地方 —— 但那样每个 dao 函数都要多一个参数，对这个体量的项目没必要。

**`ErrNotFound` 与 `translate()`（第 15、23-28 行）—— 错误翻译**
- GORM 查不到记录时返回 `gorm.ErrRecordNotFound`。如果让它一路上传到 service，service 就得 `import gorm` 才能判断 —— 上层的代码就跟"具体用了哪个数据库库"绑死了。
- `translate` 把它换成自定义的 `dao.ErrNotFound`：**上层只认识 `dao.ErrNotFound`，换数据库（比如从 GORM 换成别的 ORM）只需要改 `translate` 这一个函数**。
- 每个查询函数都用 `translate(err)` 包一层再返回（见下两个文件）。

### 5.5.2 `dao/item_dao.go`

**完整代码**：

```go
package dao

import (
	"lostfound/models"

	"gorm.io/gorm"
)

// CreateItem 新增帖子
func CreateItem(item *models.Item) error {
	return DB.Create(item).Error
}

// GetItemByID 按主键查询帖子
func GetItemByID(id uint) (*models.Item, error) {
	var item models.Item
	if err := DB.First(&item, id).Error; err != nil {
		return nil, translate(err)
	}
	return &item, nil
}

// ListItems 按条件分页查询，返回（当页数据, 总数, 错误）
func ListItems(q models.ItemListQuery) ([]models.Item, int64, error) {
	// build 是一个闭包（能"记住"外部变量的函数），每次调用都重新拼一遍查询条件。
	// 为什么要建两次？因为查总数和查数据是两条独立的 SQL，
	// 复用同一个 *gorm.DB 链条容易被前面的 Limit/Offset 污染
	// （初学者最经典的 bug：先 Limit 再 Count，total 永远等于 page_size）
	build := func() *gorm.DB {
		tx := DB.Model(&models.Item{})

		if q.Keyword != "" {
			// LIKE 模糊匹配：两端加 % 表示"包含"，物品名称或描述命中都算
			like := "%" + q.Keyword + "%"
			tx = tx.Where("title LIKE ? OR description LIKE ?", like, like)
		}
		if q.Type != "" {
			tx = tx.Where("type = ?", q.Type)
		}
		if q.Category != "" {
			tx = tx.Where("category = ?", q.Category)
		}
		if q.Campus != "" {
			tx = tx.Where("campus = ?", q.Campus)
		}
		if q.Place != "" {
			tx = tx.Where("place LIKE ?", "%"+q.Place+"%")
		}
		if q.Status != "" {
			tx = tx.Where("status = ?", q.Status)
		}
		if q.UserID != 0 {
			tx = tx.Where("user_id = ?", q.UserID)
		}
		return tx
	}

	// 1. 先数总数（前端靠它判断"还有没有下一页"）
	var total int64
	if err := build().Count(&total).Error; err != nil {
		return nil, 0, err
	}

	// 2. 再取当页数据：ORDER BY created_at DESC + LIMIT + OFFSET
	// ★ items 用 make(..., 0) 初始化而不是 var 声明：
	//   查不到数据时，前者序列化成 []，后者是 null —— 前端拿到 null 调 .map() 会直接崩
	items := make([]models.Item, 0)
	err := build().
		Order("created_at DESC").
		Limit(q.PageSize).
		Offset((q.Page - 1) * q.PageSize).
		Find(&items).Error
	if err != nil {
		return nil, 0, err
	}
	return items, total, nil
}

// UpdateItemFields 按字段 map 更新帖子
// 用 map 而不是结构体：GORM 的 Updates 传结构体会**忽略零值字段**（空字符串、0），
// 传 map 才能把某个字段改成空
func UpdateItemFields(id uint, fields map[string]any) error {
	return DB.Model(&models.Item{}).Where("id = ?", id).Updates(fields).Error
}

// DeleteItem 删除帖子
func DeleteItem(id uint) error {
	return DB.Delete(&models.Item{}, id).Error
}
```

**逐段说明**：

**`CreateItem()`（第 10-12 行）**
- `DB.Create(item)`：GORM 把结构体转成 `INSERT INTO items (...) VALUES (...)`。
- 入库成功后，GORM 把数据库生成的自增主键**回填**到 `item.ID`，调用方（service）拿到的对象就有 ID 了。
- `.Error`：GORM 的方法链最后一个方法返回 `*gorm.DB`，错误存在它的 `.Error` 字段里。

**`GetItemByID()`（第 15-21 行）**
- `DB.First(&item, id)`：按主键查第一条。GORM 生成 `SELECT * FROM items WHERE id = ? ORDER BY id LIMIT 1`。
- 查不到时 GORM 返回 `ErrRecordNotFound`，经 `translate` 换成 `dao.ErrNotFound` —— service 就是靠这个判断"帖子不存在"。

**`ListItems()`（第 24-77 行）—— 最复杂的一个**

**`build` 闭包（第 29-56 行）**：
- 闭包 = 能"记住"外部变量的函数。这里 `build` 记住了参数 `q`，每次调用都**重新拼一遍** WHERE 条件，返回一个新的查询链。
- 为什么封装成函数而不是直接写一遍：查总数和查数据需要**两条 WHERE 条件完全相同的 SQL**，抽成 `build()` 就不用把一堆 `if` 写两遍。
- 为什么调用两次（`build()` 出现两次）而不是复用同一个 `tx`：GORM 的方法链是有状态的，如果先 `.Limit(10)` 再拿同一条链去 `Count`，SQL 会变成 `SELECT COUNT(*) ... LIMIT 10` —— 总数永远是 10（经典的初学者 bug）。每次从零重建，互相不污染。
- 每条 `if q.Xxx != ""` 的规则：**条件为空就跳过这个过滤**。所以前端不传 keyword 时，SQL 里就没有 `LIKE` 那一项。
- `LIKE "%关键词%"`：两端加 `%` 表示"包含匹配"。`title LIKE ? OR description LIKE ?` 表示物品名称或描述命中任一即可。
- 所有值都用 `?` 占位符传参，**绝不拼接字符串** —— 这是防 SQL 注入的生命线（详见第六章）。

**查总数（第 59-62 行）**：
- `build().Count(&total)`：生成 `SELECT COUNT(*) FROM items WHERE ...`，结果写进 `total`。前端靠它算"共几页、有没有下一页"。

**查当页数据（第 67-75 行）**：
- `Order("created_at DESC")`：按创建时间倒序（新的在前）。
- `Limit(q.PageSize)`：这一页要几条。
- `Offset((q.Page - 1) * q.PageSize)`：跳过前面几页的数据。第 1 页 offset 0，第 2 页 offset = pageSize。
- `items := make([]models.Item, 0)`：**用 `make(..., 0)` 初始化，不用 `var items []models.Item`**。区别在"查不到数据"时：前者序列化成 JSON 是 `[]`，后者是 `null`。前端代码拿到 `null` 再调 `.map()` 会直接报错 —— 一个空数组初始化就能避免的线上 bug。

**`UpdateItemFields()`（第 82-84 行）**
- `DB.Model(&models.Item{}).Where("id = ?", id).Updates(fields)`：生成 `UPDATE items SET ... WHERE id = ?`，SET 哪些列由 `fields` map 决定。
- **为什么参数是 map 不是结构体**：GORM 的 `Updates` 传结构体时会**忽略零值字段**（空字符串、0、false）。比如想把 description 改成空字符串，传结构体的话 GORM 认为"这是零值，用户没填"，直接跳过 —— 根本改不掉。传 map 则"写了什么就更新什么"。
- 这个函数被 service 复用：改状态（`{"status": ...}`）和编辑（多个字段）都走它。

**`DeleteItem()`（第 87-89 行）**
- `DB.Delete(&models.Item{}, id)`：按主键删除。本项目是**硬删除**（`DELETE FROM items WHERE id = ?`），没做软删除（GORM 的 `gorm.DeletedAt` 字段能实现"标记删除"）。

**逐段说明**：

**三组枚举常量（第 8-35 行）**
- 写法：先定义自定义类型（`type ItemType string`），再定义该类型的常量。
- 为什么不用裸字符串：写错 `"serching"` 编译能过、上线才发现；用常量 `models.StatusSearching` 写错则**编译期直接报错**。另外 IDE 能自动补全，改值只改一处。
- 类型安全：`ItemStatus` 和 `ItemType` 是不同的类型，把 `ItemType` 的值赋给 `ItemStatus` 变量会编译报错，防张冠李戴。

**`Item` 表模型（第 38-55 行）**
- 每个字段后面挂三种 tag，被三个不同的工具读取：

| tag | 谁读 | 什么时候读 | 作用 |
|---|---|---|---|
| `gorm:"..."` | GORM | 启动建表 / 每次读写 | 列类型、非空、索引、默认值 |
| `json:"..."` | Go 的 JSON 库 | 序列化/反序列化 | 输出成什么 key 名；`"-"` = 永不输出 |
| `binding:"..."` | Gin 的校验器 | 收到请求时 | 必填、长度、枚举值 |

- `primaryKey`：主键（自增）。
- `index`：给这列建索引，加速 `WHERE type = ?` 这类查询。`type`/`category`/`campus`/`status`/`user_id` 都建了索引 —— 因为列表页就是按这些列筛的。
- `default:searching`：数据库层面的默认值（即使有代码绕过 service 直接 INSERT，状态也有兜底）。
- **`Contact` 的 `json:"-"`（第 49 行）**：整个项目最重要的安全设计之一。任何接口只要返回 `Item` 结构体，序列化时 `contact` 字段**自动消失** —— 不是"记得别返回"，是结构上返回不了。想拿联系方式只能走专门的 `GET /api/items/:id/contact`（需登录）。
- `CreatedAt`/`UpdatedAt`：GORM 约定俗成的字段名 —— 创建和更新时自动填时间，不用手动赋值。

**`ItemDetailResponse`（第 60-64 行）**
- 内嵌 `Item`（不是命名字段）：序列化时 Item 的字段会**平铺**到同一层 JSON（`id`、`title`... 和 `publisher_nickname` 并列），而不是嵌套在 `item` 键下面。
- 两个额外字段在 service 的 `GetItemDetail` 里填充。

**`ItemListQuery`（第 67-77 行）**
- 列表接口的"参数包"：controller 从 URL 收集，一路传给 dao 拼 SQL。
- 约定：字符串空值 = "这个条件不用"；`UserID` 非 0 = "只看这个用户的"。

**`CreateItemRequest`（第 80-89 行）**
- 前端发布的请求体。注意**没有** `status` 和 `user_id` 字段 —— 想传都没地方传（状态和归属由后端定，见 5.4）。
- `binding` 规则：`required`（必填）、`oneof=lost found`（枚举）、`max=64`（长度上限）。不满足时 `ShouldBindJSON` 返回错误，controller 直接 400。
- `HappenedAt` 用 `string` 收而不是 `time.Time`：前端传来的时间格式五花八门（详见 5.7 的 `ParseTime`），统一用字符串收、service 里解析。

**`UpdateItemRequest`（第 94-102 行）**
- 全字段 `omitempty`：不传就跳过校验（"部分更新"的请求体）。不传的字段在 Go 里是零值（空字符串），service 靠 `!= ""` 判断"要不要改"。
- 故意没有 `type` 和 `status`：类型不可改，状态只能走专门的接口。

**`UpdateStatusRequest`（第 105-107 行）**
- 只有一个字段，`oneof` 限制只能是三个合法状态之一。非法值（比如 `"deleted"`）在绑定阶段就被拦下，根本到不了 service。

import "time"

// User 对应数据库里的 users 表
// 结构体（struct）是"把一组相关的数据打包成一个整体"；GORM 靠它自动建表/读写

	StudentID string    `gorm:"type:varchar(32)" json:"student_id"`
	CreatedAt time.Time `json:"created_at"`
}

// ---------- 请求结构体：前端发过来的 JSON 长什么样 ----------
// `binding:"..."` 是参数校验规则，Gin 会自动检查：
//   required = 必填；min/max = 长度范围

// RegisterRequest 注册请求体
type RegisterRequest struct {
	Username  string `json:"username" binding:"required,min=3,max=20"`
	Password  string `json:"password" binding:"required,min=6,max=32"`
	Nickname  string `json:"nickname" binding:"max=32"`
	StudentID string `json:"student_id" binding:"max=32"`
}

// LoginRequest 登录请求体

	Username string `json:"username" binding:"required"`
	Password string `json:"password" binding:"required"`

**逐段说明**：

**`User` 表模型（第 8-16 行）**
- `Username` 的 `uniqueIndex`：数据库层面建唯一索引 —— 就算应用层的查重被绕过（并发注册），数据库也会拒绝重复用户名。**双保险**。
- **`Password` 的 `json:"-"`（第 11 行）**：存的是 bcrypt 哈希值，序列化时永不输出 —— 注册/登录接口返回用户信息时，密码哈希自动被剔除。
- `Nickname`/`StudentID` 选填（没有 `not null`）。
- GORM 的命名约定：字段名 `StudentID` → 列名 `student_id`（驼峰自动转下划线），不用额外配置。

**`RegisterRequest`（第 23-28 行）**
- `binding` 规则在前端和后端**都会**被执行：前端有 JS 校验（体验好），但**后端的校验才是安全边界** —— 绕过前端直接调 API 时，只有后端的 `binding` 拦得住。
- 密码限制 6-32 位：下限防太弱，上限防"超长字符串"攻击 bcrypt 的算力。

**`LoginRequest`（第 31-34 行）**
- 登录只校验"非空"：登录时密码规则不该校验长度（老账号的密码可能不符合新规则），只要求两个字段都传了。

### 5.7.1 `utils/response.go`

**完整代码**：

```go
package utils

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

// 业务错误码：0 = 成功，其余按含义分类
// 用常量代替魔法数字，前端和文档都对着这份清单写
const (
	CodeSuccess = 0

	CodeInvalidParam   = 1001 // 参数错误
	CodeUnauthorized   = 1002 // 未登录 / token 无效
	CodeForbidden      = 1003 // 没有权限（比如想改别人的帖子）
	CodeNotFound       = 1004 // 资源不存在
	CodeUsernameTaken  = 1005 // 用户名已被注册
	CodeWrongPassword  = 1006 // 用户名或密码错误
	CodeStatusBackward = 1007 // 状态只能前进，不能回退
	CodeServerError    = 1008 // 服务器内部错误
)

// Response 是所有接口统一的响应结构
// 字段名首字母大写才能被 JSON 序列化；`json:"xxx"` 决定输出时的 key 名
type Response struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data"` // any 是 interface{} 的简写（Go 1.18+），表示"任意类型"
}

// OK 成功响应（message 固定为 "ok"）
func OK(c *gin.Context, data any) {
	OKMsg(c, "ok", data)
}

// OKMsg 成功响应（自定义 message）
func OKMsg(c *gin.Context, message string, data any) {
	c.JSON(http.StatusOK, Response{Code: CodeSuccess, Message: message, Data: data})
}

// Fail 失败响应：业务码 + 对应的 HTTP 状态码（401/403/404/400/500）
func Fail(c *gin.Context, code int, message string) {
	c.JSON(httpStatus(code), Response{Code: code, Message: message, Data: nil})
}

// httpStatus 把业务码映射成 HTTP 状态码
// 好处：Apifox 里一眼能看出哪些接口是 401/403，前端也能用统一逻辑判断
func httpStatus(code int) int {
	switch code {
	case CodeUnauthorized:
		return http.StatusUnauthorized // 401
	case CodeForbidden:
		return http.StatusForbidden // 403
	case CodeNotFound:
		return http.StatusNotFound // 404
	case CodeServerError:
		return http.StatusInternalServerError // 500
	default:
		return http.StatusBadRequest // 400
	}
}
```

**逐段说明**：

**业务错误码（第 11-22 行）**
- 0 = 成功；1001~1008 分别对应一种失败情况。用常量而不是数字，代码里写 `utils.CodeForbidden` 一眼知道含义。
- 这份清单是**前后端共用**的约定：前端根据 code 决定弹什么提示，API 文档里也列这份表。

**`Response` 统一响应结构（第 26-30 行）**
- 所有 12 个接口的成功/失败响应都是这个形状：`{code, message, data}`。
- 前端只需要写一次解析逻辑：`if (data.code !== 0) { 弹 message; } else { 用 data.data }`。如果每个接口各返回各的格式，前端就得给每个接口写一套。
- `Data any`：任意类型 —— 列表接口塞数组、详情塞对象、改状态塞 nil，共用一个字段。

**`OK` / `OKMsg`（第 33-40 行）**
- 两个成功响应函数，区别只是 message：`OK` 固定 `"ok"`，`OKMsg` 自定义（如"发布成功"）。
- 都返回 HTTP 200 + `code: 0`。

**`Fail`（第 43-45 行）**
- 参数是**业务码**，函数内部调 `httpStatus` 换算成 HTTP 状态码，`data` 固定为 nil。

**`httpStatus`（第 49-62 行）—— 两套状态码的换算**
- 为什么响应里既有业务码又有 HTTP 状态码：
  - **业务码**（1001~1008）精细，给**前端代码**看 —— 决定具体提示文案。
  - **HTTP 状态码**（400/401/403/404/500）粗粒度，给**通用工具**看 —— 浏览器、Apifox、监控系统、Nginx 日志。如果所有失败都返回 HTTP 200，这些工具就全瞎了（Apifox 里看不出哪些接口要登录，监控统计不出错误率）。
- `default: 400`：没列出的业务码（如 1005 用户名已注册、1007 状态回退）都归 400 —— 它们本质上都是"请求参数/操作不合法"。

### 5.7.2 `utils/jwt.go`

**完整代码**：

```go
package utils

import (
	"errors"
	"fmt"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

// CustomClaims 自定义载荷：除了标准字段，额外带上"这是哪个用户"
// 内嵌 jwt.RegisteredClaims 后，就自动有了 exp（过期时间）、iat（签发时间）等标准字段
type CustomClaims struct {
	UserID   uint   `json:"user_id"`
	Username string `json:"username"`
	jwt.RegisteredClaims
}

// ErrTokenInvalid token 无效
var ErrTokenInvalid = errors.New("token 无效")

// 包级变量：启动时由 InitJWT 注入一次，之后只读
// （小项目常见的简化写法；大项目会用依赖注入把配置传进每个需要的地方）
var (
	jwtSecret     []byte
	jwtExpireHour int
)

// InitJWT 在 main 启动时调用一次，把配置里的密钥和有效期装进来
func InitJWT(secret string, expireHours int) {
	jwtSecret = []byte(secret)
	jwtExpireHour = expireHours
}

// GenToken 生成 token：把用户信息 + 过期时间打包，用密钥签名
func GenToken(userID uint, username string) (string, error) {
	claims := CustomClaims{
		UserID:   userID,
		Username: username,
		RegisteredClaims: jwt.RegisteredClaims{
			ExpiresAt: jwt.NewNumericDate(time.Now().Add(time.Duration(jwtExpireHour) * time.Hour)),
			IssuedAt:  jwt.NewNumericDate(time.Now()),
		},
	}
	// HS256 = 对称加密：同一个密钥既用来签名也用来验证
	token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
	return token.SignedString(jwtSecret)
}

// ParseToken 解析并校验 token：签名对不对？过期没有？
func ParseToken(tokenString string) (*CustomClaims, error) {
	token, err := jwt.ParseWithClaims(tokenString, &CustomClaims{}, func(t *jwt.Token) (any, error) {
		// 安全校验：确认对方用的就是 HS256，防止有人伪造算法（经典攻击手法）
		if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
			return nil, fmt.Errorf("非预期的签名算法: %v", t.Header["alg"])
		}
		return jwtSecret, nil
	})
	if err != nil {
		return nil, err
	}

	// 类型断言：把接口类型的 Claims 转回我们自己的 CustomClaims
	claims, ok := token.Claims.(*CustomClaims)
	if !ok || !token.Valid {
		return nil, ErrTokenInvalid
	}
	return claims, nil
}
```

**逐段说明**：

**JWT 是什么（理解本文件的前提）**
- 一个字符串，形如 `xxx.yyy.zzz`（三段用点分隔）：第一段是头部（说明用什么算法），第二段是载荷（存了哪些数据），第三段是**签名**。
- 服务端用密钥对前两段做签名。任何人改了载荷里的内容（比如把 user_id 从 2 改成 1），签名就对不上，`ParseToken` 会报错 —— **这就是"token 不可伪造"的原理**。
- 注意：载荷只是 Base64 编码，**没有加密** —— 谁都能解码看到里面的 user_id。所以 token 里不放敏感信息（密码之类），它只解决"防篡改"，不解决"防偷看"。

**`CustomClaims`（第 13-17 行）**
- 载荷结构：自定义两个字段（`user_id`、`username`）+ 内嵌 `jwt.RegisteredClaims`（标准字段：`exp` 过期时间、`iat` 签发时间）。

**`InitJWT` 与包级变量（第 24-33 行）**
- 密钥和有效期存在包级变量里，`main.go` 启动时通过 `InitJWT` 注入一次。之后 `GenToken`/`ParseToken` 直接用，不用每个函数都传。
- 密钥来自 `config.yaml` 的 `jwt.secret` —— **不能硬编码在代码里**（代码会提交到 GitHub，密钥进仓库等于泄露）。线上用的是独立配置的另一个密钥（见第十一章）。

**`GenToken()`（第 36-48 行）—— 签发**
- 第 37-44 行：组装载荷。`ExpiresAt` = 现在 + 配置的有效期小时数。
- 第 46-47 行：`HS256` 算法 + 密钥签名，返回最终字符串。
- 调用时机：登录成功后（`service.Login`）。

**`ParseToken()`（第 51-69 行）—— 校验**
- 第 52-58 行：`ParseWithClaims` 一边解析一边验签。第三个参数是回调函数，返回"用什么密钥来验" —— 同时在里面检查算法：
  - `t.Method.(*jwt.SigningMethodHMAC)`：确认对方声明的算法是 HMAC 家族（HS256 属于它）。**不检查会有一个经典攻击**：攻击者把头部算法改成 `none`（无签名）或非对称算法，骗过校验逻辑。这是 JWT 库文档里专门警告的点。
- 验签失败（被篡改）或过期，`err != nil`，直接返回错误 —— 中间件收到后返回 401。
- 第 63-68 行：类型断言把接口类型转回 `CustomClaims`，再确认 `token.Valid`。返回解析好的 claims，中间件从里面取 `UserID` 放进 Context。

### 5.7.3 `utils/password.go`

**完整代码**：

```go
package utils

import "golang.org/x/crypto/bcrypt"

// HashPassword 把明文密码加密成哈希值
// bcrypt 的特点：自带随机盐 —— 同一个密码每次加密结果都不同，所以数据库泄露了也难被"查表"破解
func HashPassword(plain string) (string, error) {
	bytes, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
	return string(bytes), err
}

// CheckPassword 校验"明文密码"和"数据库里的哈希"是否匹配
// bcrypt 自己会从哈希里取出盐来重新计算，所以不需要我们单独存盐
func CheckPassword(plain, hash string) bool {
	return bcrypt.CompareHashAndPassword([]byte(hash), []byte(plain)) == nil
}
```

**逐段说明**：
- `HashPassword`：注册时用。**数据库里永远只存哈希值，不存明文** —— 就算数据库泄露，攻击者也拿不到原始密码。
- **"盐"是什么**：加密前往密码里掺的一段随机数据。没有盐的话，同一个密码的哈希永远相同 —— 攻击者可以拿"常见密码表"（彩虹表）反查。bcrypt 自带随机盐：**同一个密码每次加密结果都不同**，彩虹表失效。
- `CheckPassword`：登录时用。不需要我们手动取盐 —— bcrypt 的哈希字符串里已经包含了盐，`CompareHashAndPassword` 自己会解析出来重新计算比对。
- 注意 `bcrypt.DefaultCost`：bcrypt 故意算得慢（约 100ms 一次），这是特性不是缺陷 —— 慢让暴力破解的代价高到不可行。
- 两个函数的返回值：加密返回 `(哈希, error)`；校验返回 `bool`（匹配与否），不返回 error（"不匹配"就是 false，不是错误）。

### 5.7.4 `utils/time.go`

**完整代码**：

```go
package utils

import (
	"fmt"
	"time"
)

// timeLayouts 前端可能传来的几种时间格式，挨个尝试
// Go 的时间格式不用 yyyy-MM-dd，而是用"参考时间" 2006-01-02 15:04:05 来当模板（记住这个数就行）
var timeLayouts = []string{
	time.RFC3339,          // 2026-09-26T14:30:00+08:00
	"2006-01-02T15:04:05", // 2026-09-26T14:30:00
	"2006-01-02T15:04",    // 2026-09-26T14:30（<input type="datetime-local"> 的原生格式）
	"2006-01-02 15:04:05", // 2026-09-26 14:30:00
	"2006-01-02 15:04",    // 2026-09-26 14:30
	"2006-01-02",          // 2026-09-26
}

// ParseTime 把前端传来的时间字符串解析成 time.Time
func ParseTime(s string) (time.Time, error) {
	for _, layout := range timeLayouts {
		// ParseInLocation：按本地时区解析（不加这个，时间会差 8 小时）
		if t, err := time.ParseInLocation(layout, s, time.Local); err == nil {
			return t, nil
		}
	}
	return time.Time{}, fmt.Errorf("无法识别的时间格式: %s", s)
}
```

**逐段说明**：
- **Go 时间格式的特殊写法**：不用 `yyyy-MM-dd`，而是拿一个固定的"参考时间" `2006-01-02 15:04:05` 当模板 —— 它恰好是 1 月 2 日 3 点 4 分 5 秒（递增好记）。想格式化/解析什么形状，就把参考时间按那个形状摆。
- `timeLayouts`：前端可能传来的 6 种格式。HTML 的 `<input type="datetime-local">` 控件原生给的是 `2006-01-02T15:04` 这种形状，但用户手输、或别的前端代码可能给出别的形状，所以列了常见几种。
- `ParseTime` 的逻辑就是**挨个试**：哪个 layout 解析成功就用哪个；全失败返回错误（service 里翻成 `ErrBadTime`）。
- `ParseInLocation(..., time.Local)`：按本地时区解析。**不加这个会差 8 小时**（默认按 UTC 解析，中国是 UTC+8）。
- 为什么用字符串收时间而不是让 `ShouldBindJSON` 直接绑定 `time.Time`：前端格式不可控，用字符串收、这里统一转换，兼容性最好。

## 5.8 一层一层的调用链回顾

以"发布一条失物信息"为例，把五层串起来：

| 步骤 | 层 | 干什么 |
|---|---|---|
| 1 | router | `POST /api/items` 匹配到 `JWTAuth + CreateItem` |
| 2 | middleware | 验 token，把 `user_id` 放进 Context |
| 3 | controller | `ShouldBindJSON` 解析 + 校验请求体，取 `user_id`，调 service |
| 4 | service | 解析时间、组装 `Item`（状态和归属写死），调 dao |
| 5 | dao | `INSERT INTO items ...` |
| 6 | 返回路上 | dao 回填 ID → service 返回 item → controller `utils.OKMsg` 发响应 |

每一层只跟**相邻的下一层**打交道，改一层不影响其他层 —— 这就是分层的意义。

# 第六章 四个关键设计（面试官大概率问）

## 6.1 密码是怎么存的？

**❌ 错误做法**：明文存。数据库泄露 = 所有用户密码泄露。

**✅ 我们的做法**：bcrypt 哈希。

```go
// utils/password.go
func HashPassword(plain string) (string, error) {
    bytes, err := bcrypt.GenerateFromPassword([]byte(plain), bcrypt.DefaultCost)
    return string(bytes), err
}

func CheckPassword(plain, hash string) bool {
    return bcrypt.CompareHashAndPassword([]byte(hash), []byte(plain)) == nil
}
```

注册时：`明文密码` → `HashPassword` → 存进库。
数据库里长这样（谁也看不出原密码是什么）：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

登录时：`用户输入的明文` + `库里的哈希` → `CheckPassword` → 返回 true/false。

**为什么不用 MD5 / SHA256？**

| | MD5 / SHA256 | bcrypt |
|---|---|---|
| 速度 | **快**（显卡一秒能算几十亿次） | **慢**（故意设计得慢） |
| 盐 | 需要自己加 | **自带随机盐** |
| 抗暴力破解 | 弱 | 强 |

黑客拿到哈希后想"反推出原密码"，只能一个个猜。**算得越慢，他越难**。
bcrypt 故意把每次计算拖慢到约 0.1 秒 —— 对正常登录没影响，
但黑客想试一亿个密码就得好几年。

**"自带随机盐"是什么意思？** 同一个密码 `123456`，两个用户加密出来的结果**完全不同**：

```
用户A：$2a$10$N9qo8uLOickgx2ZMRZoMye...
用户B：$2a$10$Xk7pQ3mNvB1cD4fG6hJ8kL...
```

所以黑客也没法"查表"（提前算好常见密码的哈希，拿去比对）。

## 6.2 联系方式为什么"看不到"？

**需求**（PRD 4.5）：联系方式不在列表和详情里展示，**登录后**才能通过"查看联系方式"看到。

**我们的做法**：`json:"-"`（第四章已经讲过，这里再总结一遍）。

```go
// models/item.go
Contact string `gorm:"type:varchar(100);not null" json:"-"`
```

**三个层次的安全性**：

| 层次 | 做法 | 效果 |
|---|---|---|
| 存储 | `gorm` 标签正常 | 数据库里存着，没问题 |
| **输出** | **`json:"-"`** | **任何返回 Item 的接口都自动不带它** |
| 访问 | 独立接口 + 登录中间件 | 想拿？先登录 |

**面试官可能问**："我未登录，能不能改 URL 拿到别人的联系方式？"

**答**：
> 不能。列表和详情的响应结构里**根本没有这个字段** —— 不是"查出来再过滤掉"，
> 是序列化时就跳过了。唯一的出口是 `GET /api/items/:id/contact`，
> 而这个接口挂了 `JWTAuth` 中间件，没有有效 token 直接返回 401。

**如果面试官追问**："那我把 token 伪造一下呢？"

**答**：
> 伪造不了。token 的第三段是签名，用服务器才知道的密钥算出来的。
> 服务器每次收到 token 都会重新算一遍签名，对不上就拒绝（`utils/jwt.go` 里会验）。

## 6.3 状态为什么不能回退？

**需求**（PRD 4.4）：`寻找中 → 已找到 → 已结束`，**只能前进不能回退**。

**实现**（`service/item_service.go`）：

```go
var statusOrder = map[models.ItemStatus]int{
    models.StatusSearching: 0,
    models.StatusResolved:  1,
    models.StatusClosed:    2,
}

func UpdateStatus(userID, itemID uint, newStatus models.ItemStatus) error {
    // ... 先查帖子、校验是不是本人 ...

    if statusOrder[newStatus] <= statusOrder[item.Status] {
        return ErrStatusBackward    // 序号没变大 → 拒绝
    }
    return dao.UpdateItemFields(itemID, map[string]any{"status": newStatus})
}
```

**为什么用"序号比较"而不是写一堆 if-else？**

如果写 if-else，规则是：`寻找中→已找到` ✅、`已找到→已结束` ✅、
`寻找中→已结束` ✅（跳过一级也算前进）、`已找到→寻找中` ❌……

三个状态就要写 6 种情况的判断。**用序号只写一行**：

```
新状态序号 > 当前状态序号  →  允许
```

将来加第四个状态，只要往 map 里加一行，判断逻辑不用改。

**配套的坑（很重要）**：编辑接口 `PUT /api/items/:id` **故意不给改 status**。

```go
// models/item.go
type UpdateItemRequest struct {
    Title       string `json:"title" ...`
    // ... 注意：没有 Status 字段！
}
```

如果编辑接口能改 status，用户 `PUT` 一下就能把"已结束"改回"寻找中"，
状态机就形同虚设了。

## 6.4 退出登录为什么"什么都没做"？

看 `controller/user_controller.go` 的 `Logout`：

```go
func Logout(c *gin.Context) {
    utils.OKMsg(c, "已退出登录（前端请删除本地保存的 token）", nil)
}
```

**它真的什么都没做** —— 但这是**正确**的，不是偷懒。

**原因**：JWT 是**无状态**的。

| | 传统 Session | JWT（我们用的） |
|---|---|---|
| 服务端存记录吗 | ✅ 存（记着"谁登录了"） | ❌ 不存 |
| 退出登录怎么做 | 删掉服务端的记录 | **服务端没法删（没记录可删）** |
| 能强制下线吗 | ✅ 能 | ❌ 不能（除非额外上 Redis 黑名单） |

**打个比方**：
- Session 像**酒店房卡**：退房时前台把卡注销，卡就失效了
- JWT 像**演唱会门票**：票在你手上，主办方**没法让已经卖出去的票作废**

所以"退出登录"真正发生的地方是**前端**：把本地存的 token 删掉，
之后的请求就不带它了（也就相当于"未登录"了）。

**保留这个接口的意义**：
1. 满足任务书"退出登录"的要求
2. 前端有一个统一的收尾调用点
3. 将来如果改成 Redis 黑名单方案，前端代码不用动

**面试官可能问**："那用户 token 被盗了怎么办？"

**答**：
> 这正是 JWT 的取舍。要解决得引入 Redis 黑名单：把要作废的 token 存起来，
> 每次请求查一下。但那样就失去了 JWT"无状态、不用查库"的优势。
> 我们项目规模小，选择了简单方案；token 有效期设的是 7 天。

# 第七章 前端是怎么工作的

前面六章都在讲后端。这一章补上另一半：**用户直接看到的那部分（前端）是怎么动起来的**。

## 7.1 前端三件套：各管什么

前端就是三个东西，各管一摊：

| 文件类型 | 管什么 | 类比 |
|---|---|---|
| **HTML**（`.html`） | **结构**：页面上有哪些东西 | 房子的**骨架**（哪里是墙、哪里是门） |
| **CSS**（`.css`） | **样式**：这些东西长什么样 | 房子的**装修**（颜色、大小、间距） |
| **JavaScript**（`.js`） | **行为**：用户操作时发生什么 | 房子的**水电**（按开关灯就亮） |

打开我们的 `web/index.html` 看：

```html
<!-- ① 结构：有哪些东西 -->
<div class="search-wrap">
  <div class="search-box">
    <span class="icon">🔍</span>
    <input id="keyword" type="search" placeholder="搜一搜：校园卡、耳机、钥匙…">
  </div>
</div>

<!-- ② 引入样式 -->
<link rel="stylesheet" href="css/style.css">

<!-- ③ 引入行为 -->
<script src="js/api.js"></script>
<script src="js/index.js"></script>
```

**HTML 里那些 `class="..."` 是干嘛的？**
它们本身不影响显示，只是**给 CSS 和 JS 打的"标记"** ——
CSS 靠它找到元素来上色，JS 靠它找到元素来绑定点击事件。

## 7.2 一个页面从打开到显示的完整过程

这是理解前端的**关键**，一定要搞懂：

```
① 你在浏览器输入 http://localhost:8080/app/
        ↓
② 服务器返回 index.html 的文本内容
        ↓
③ 浏览器开始解析这份 HTML，遇到 <link> 就去下载 CSS
   （下载期间它不会傻等，继续往下解析）
        ↓
④ 遇到 <script> 就去下载 JS 文件
        ↓
⑤ 浏览器按 HTML + CSS 把界面**画出来**
   ⚠️ 注意：此时列表区域是空的！因为数据还没拿到
        ↓
⑥ JS 开始执行：调用后端接口 /api/items 拿数据
        ↓
⑦ 拿到数据后，JS 把数据"拼"成 HTML 字符串，塞进页面
        ↓
⑧ 你看到完整的列表
```

**核心认知：页面是先画出来、数据后填进去的。**

```js
// web/js/index.js —— 第 ⑦ 步干的事
box.innerHTML = state.list.map(cardHtml).join('');
//              ↑ 把数组里的每条数据，用 cardHtml() 拼成 HTML，一起塞进页面
```

```js
// cardHtml 就是"数据 → HTML"的模板
function cardHtml(item) {
  return `
    <div class="card" data-id="${item.id}">
      <span class="tag ${item.type}">${TYPE_TEXT[item.type]}</span>
      <span class="card-title">${escapeHtml(item.title)}</span>
      <span class="badge ${item.status}">${statusText(item)}</span>
    </div>
  `;
}
```

> **为什么要这样设计？**
> 因为数据是**变的**（今天 3 条帖子，明天 30 条）。
> 如果 HTML 里写死内容，每来一条新数据都得改网页文件。
>
> 现在这样：**HTML 只写"空壳"，JS 负责把数据填进去** ——
> 这叫"**前后端分离**"，页面文件不用动，数据变了页面自动变。

## 7.3 前端怎么跟后端说话：`fetch`

浏览器内置了一个函数叫 `fetch`，专门用来发 HTTP 请求：

```js
// 最简形式：GET 请求
const res  = await fetch('http://localhost:8080/api/items');
const data = await res.json();     // 把响应的 JSON 文本解析成对象
```

拆开看：

| 部分 | 含义 |
|---|---|
| `fetch(地址)` | 发一条 HTTP 请求（默认是 GET） |
| `await` | "等结果回来再往下走"（网络请求要时间，不能立刻拿到） |
| `res` | 服务器的响应对象 |
| `res.json()` | 把响应体里的 JSON **文本**解析成 JS 对象 |

**发 POST 请求（带数据）**：

```js
const res = await fetch('http://localhost:8080/api/items', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ title: '校园卡', type: 'lost' }),   // 对象 → JSON 文本
});
```

> **`JSON.stringify()` 和 `res.json()` 是一对反操作**：
> - `JSON.stringify(对象)` → JSON **文本**（发给后端）
> - `res.json()` → 把文本变回**对象**（后端发来的）

我们在 `web/js/api.js` 里把 fetch **包了一层**，这样每个页面就不用重复写这些：

```js
async function request(method, path, body, opts = {}) {
  // ① 自动带上 token
  const headers = { 'Content-Type': 'application/json' };
  const token = getToken();
  if (token) headers['Authorization'] = 'Bearer ' + token;

  // ② 发请求
  const res = await fetch(API_BASE + path, { method, headers, body: ... });

  // ③ 自动解析 JSON
  const data = await res.json();

  // ④ 自动处理 401（登录过期）
  if (res.status === 401) {
    clearToken();
    toast('请先登录');
    setTimeout(() => location.href = 'login.html', 700);
    throw new Error(data.message);
  }

  // ⑤ 自动判断业务错误
  if (data.code !== 0) throw new Error(data.message);

  return data.data;     // ⑥ 只把有用的部分返回给页面
}
```

**包这一层的好处**：页面代码变成这样，干净得多：

```js
// 页面里只要写这一行，token、解析、错误处理全自动
const data = await api.get('/items?page=1');
```

## 7.4 token 存在哪？怎么自动带上？

**存哪**：浏览器的 `localStorage`（本地存储，关掉浏览器再打开还在）。

```js
localStorage.setItem('lostfound_token', token);   // 存
localStorage.getItem('lostfound_token');          // 取
localStorage.removeItem('lostfound_token');       // 删（退出登录）
```

**怎么自动带上**：在 `api.js` 的 `request()` 里，每次请求前自动加请求头：

```js
if (token) headers['Authorization'] = 'Bearer ' + token;
```

所以页面代码**完全不用管 token** —— 存一次，之后所有请求自动带。

**完整的生命周期**：

```
登录成功 → setToken() 存进 localStorage
    ↓
之后每个请求 → request() 自动读出来，放进 Authorization 头
    ↓
退出登录 → clearToken() 删掉，之后的请求就不带了
    ↓
token 过期 → 后端返回 401 → api.js 自动清掉 + 跳登录页
```

> **为什么不用 Cookie？** Cookie 每次请求自动带上，但**容易被 CSRF 攻击**
> （别的网站可以诱导你的浏览器发请求，自动带上你的 Cookie）。
> 用 `localStorage` + 手动加 Header 的方式，**别的网站读不到你的 localStorage**，
> 也就伪造不了这个请求头。

# 第八章 接口：前后端之间的"合同"

第七章讲了前端怎么发请求，第四章讲了后端怎么处理请求。
这一章把它们**接起来**：**双方凭什么能对上？**

## 8.1 接口到底是什么

**一句话**：接口 = **前后端约定好的一种"对话方式"**。

打个比方 —— **点外卖**：

| 外卖 | 我们的接口 |
|---|---|
| 菜单上写着"宫保鸡丁，25 元，可选微辣/中辣/特辣" | 接口文档写着"发布接口，需要 title/type/category 等字段" |
| 你按菜单点：宫保鸡丁、中辣 | 前端按约定发：`{"title":"校园卡","type":"lost"}` |
| 商家按菜单做，端出来一盘菜 | 后端按约定处理，返回 `{"code":0,"data":{...}}` |

**关键**：**双方都得按同一份菜单来**。
你点"宫保鸡丁不要花生"，但菜单上根本没有"不要花生"这个选项 —— 商家只能忽略或报错。

## 8.2 一份接口"合同"包含哪些内容

看我们的发布接口，一份完整的"合同"有 **5 个要素**：

```http
POST /api/items                              ← ① 方法 + ② 路径
Authorization: Bearer eyJhbGciOiJIUzI1...    ← ③ 要带什么头
Content-Type: application/json
                                             ← 空行
{                                            ┐
  "type": "lost",                            │
  "title": "校园卡",                          ├ ④ 请求体：要传什么
  "category": "card",                        │
  "happened_at": "2026-10-05 14:30",         │
  "contact": "微信 xiaoming123"               │
}                                            ┘
```

⑤ **返回什么**：

```json
{
  "code": 0,
  "message": "发布成功",
  "data": { "id": 4, "title": "校园卡", "status": "searching", ... }
}
```

**五个要素缺一不可**：

| 要素 | 说清楚什么 | 不说清楚会怎样 |
|---|---|---|
| ① 方法 | 是"查"还是"新建" | 前端用 GET 发数据，后端收不到 |
| ② 路径 | 找哪个功能 | 404 |
| ③ 请求头 | 要不要登录、带什么格式 | 401 或解析失败 |
| ④ 请求体 | 要传哪些字段、什么类型、哪些必填 | 400 |
| ⑤ 响应 | 返回什么结构、错误怎么表示 | 前端不知道怎么取数据 |

**我们的这份"合同"写在哪？** 三个地方，内容必须一致：

| 位置 | 形式 | 给谁看 |
|---|---|---|
| `models/*.go` 里的结构体 | Go 代码 | **后端自己执行**（Gin 照着它解析校验） |
| `docs/API接口文档.md` | 人话文档 | **前端开发者**（照着它写请求） |
| `docs/openapi.json` | 机器可读 | **Apifox**（导入即得测试工具 + 在线文档） |

## 8.3 ★ 完整例子：点一下"查看联系方式"，背后发生了什么

这是把**前端 + 接口 + 后端**串起来的完整链路。跟着走一遍，你就全通了。

**场景**：小明在详情页看到一条别人发的失物帖，点了「查看联系方式」。

```
【前端侧】
① 用户点击按钮
   HTML:  <button id="btnContact">查看联系方式</button>
   JS:    document.getElementById('btnContact').onclick = showContact

② showContact() 开始执行，先检查"我登录了吗"
   → localStorage 里有没有 token？

   ┌─ 没有 token ─▶ 弹提示"请先登录" → 跳登录页（带上跳回地址）
   │                （登录成功后再跳回来，继续这一步）
   └─ 有 token ────▶ 继续往下

③ 发请求
   fetch('http://localhost:8080/api/items/4/contact', {
     headers: { 'Authorization': 'Bearer eyJhbGci...' }
   })

【网络】
④ 请求穿过网络，到达后端

【后端侧】—— 就是第四章讲的完整旅程
⑤ Gin 查路由表 → 命中 GET /api/items/:id/contact
⑥ 中间件 JWTAuth：验 token 签名、验过期
   → 通过：把 user_id 存进 Context，放行
   → 不通过：返回 401（前端会跳登录页）
⑦ controller.GetContact：从 URL 取出 id=4
⑧ service.GetContact：查这条帖子，取出 contact 字段
⑨ dao：SELECT contact FROM items WHERE id = 4
   （注意：这个查询专门为了拿 contact，平时查询根本不带这个字段）

【返回】
⑩ 后端返回：{"code":0,"message":"ok","data":{"contact":"微信 xiaoming123"}}

【前端侧】
⑪ fetch 拿到响应，api.js 检查 code === 0 ✓
⑫ showContact() 拿到 contact，弹出一个卡片显示
⑬ 用户看到："微信 xiaoming123"
```

**把这条链路画成图**：

```
┌─────────── 浏览器 ───────────┐        ┌────────────── 服务器 ──────────────┐
│                              │        │                                     │
│  ① 点击按钮                  │        │  ⑤ 路由匹配                         │
│  ② 检查 localStorage 有无 token│       │  ⑥ 中间件验 token                   │
│  ③ fetch 发请求 ─────────────┼───HTTP─┼─▶ ⑦ controller 取参数              │
│                              │        │  ⑧ service 取数据                   │
│                              │        │  ⑨ dao 查数据库 → MySQL             │
│  ⑪ 解析响应                  │        │                                     │
│  ⑫ 弹出卡片显示 ◀────────────┼───HTTP─┼── ⑩ 返回 {contact: "微信..."}      │
│  ⑬ 用户看到联系方式          │        │                                     │
└──────────────────────────────┘        └─────────────────────────────────────┘
```

**这个例子里藏着的设计要点**：

| 环节 | 设计 |
|---|---|
| ② 检查登录 | 前端**先拦一道**（体验好，不用白跑一趟网络） |
| ⑥ 中间件 | 后端**再拦一道**（安全底线，前端拦不住的攻击者绕不过这里） |
| ⑨ dao | **专门查询 contact**，列表/详情的查询根本不带它 |
| ⑩ 返回 | 单独一个接口、单独一个响应结构 —— **结构上保证不泄露** |

> **"前端拦一道、后端再拦一道"是标准做法**：
> 前端的校验是**为了体验**（提示更及时），后端的校验是**为了安全**（前端拦不住的人绕不过）。
> **永远不能因为"前端已经校验过了"就省掉后端校验** —— 攻击者可以直接调接口。

## 8.4 前后端怎么保证按同一份"合同"办事

**后端侧：`binding` 标签强制执行**

```go
type CreateItemRequest struct {
    Type     ItemType `json:"type" binding:"required,oneof=lost found"`
    Title    string   `json:"title" binding:"required,max=64"`
    Contact  string   `json:"contact" binding:"required,max=100"`
    // ...
}
```

前端要是不按合同来，后端**直接拒绝**（400），而不是"凑合用"。

**前端侧：照着文档写**

前端开发者拿到 `docs/API接口文档.md`，照着写请求 —— 这就是"按合同办事"。

**如果合同对不上，会发生什么**（第四章实测过的）：

| 情况 | 结果 |
|---|---|
| 字段名大小写写错 | ⚠️ 居然能成功（Go 的 JSON 解析对大小写不敏感，会宽松匹配） |
| 多传了后端不认识的字段 | ✅ 成功，多余字段**被静默忽略** |
| 少传了必填字段 | ❌ **400 报错**：`Field validation for 'Title' failed on the 'required' tag` |
| 传了非法值（如 `type: "xxx"`） | ❌ 400（`oneof` 规则拦下） |

**后端的策略**：能宽容的宽容（大小写、多余字段），**不能让步的绝不让步**（必填、取值范围）。

## 8.5 接口设计的三条经验

看我们的接口设计，有三条值得记住的做法：

**① 用 HTTP 方法和状态码"说人话"**

| 做法 | 好处 |
|---|---|
| 查用 GET、建用 POST、改用 PUT/PATCH、删用 DELETE | 光看请求第一行就知道对方想干嘛 |
| 错误返回真实状态码（401/403/404） | Apifox、监控系统、Nginx 日志都能直接用 |

**② 需要登录的接口单独标注，不要"一刀切"**

```
GET  /api/items          ← 公开：谁都能看列表
GET  /api/items/:id      ← 公开：谁都能看详情
GET  /api/items/:id/contact  ← 要登录：联系方式是隐私
POST /api/items          ← 要登录：得知道是谁发的
```

**"要不要登录"由业务决定，写在路由上**（`middleware.JWTAuth()` 挂在哪条路由上），一眼能看出来。

**③ 敏感字段用"独立接口"隔离，而不是"返回后过滤"**

这是本项目最重要的接口设计。联系方式**不在**列表/详情里返回，
专门做一个 `GET /api/items/:id/contact`。

**为什么不用"查出来再删掉"的方式？**

```go
// ❌ 危险做法：先查全部，再手动删掉敏感字段
item := dao.GetItem(id)
item.Contact = ""          // 手动清空
return item
// 哪天有人加了个新接口，忘了写这行 → 泄露！
```

```go
// ✅ 我们的做法：结构上就不可能有
type Item struct {
    Contact string `json:"-"`    // 序列化时永远跳过，谁写新接口都漏不了
}
```

**"防呆"比"小心"可靠** —— 靠人记住"别忘了删字段"迟早会出事，
靠结构保证"根本拿不到"才万无一失。

---

<details>
<summary><b>参考答案（点开）</b></summary>

**A1** 不是明文，存的是 bcrypt 哈希。
注册时 `utils.HashPassword` 加密后入库；登录时用 `utils.CheckPassword`
把"用户输入的明文"和"库里的哈希"比对。
bcrypt 自带随机盐且计算慢，即使数据库泄露也很难被破解。

**A2** 因为 `models.Item` 的 Contact 字段有 `json:"-"`，序列化时永远被跳过 ——
是**结构上**保证不可能泄露，不是"查出来再删"。
面试官那题的答案：不能。唯一出口是 `/api/items/:id/contact`，
它挂了 JWT 中间件，没 token 返回 401；token 也伪造不了（签名验证）。

**A3** 返回 `400` + `{"code":1007,"message":"状态只能前进，不能回退"}`。
因为 `UpdateStatus` 里用 `statusOrder` 比较序号，新状态必须**严格大于**当前状态。
这么设计是防误操作：手滑点了"已结束"不给改回来，宁可让你重新发一条。
（这也符合 PRD 4.4 的要求）

**A4** 一次查"总数"（`Count`），一次查"当页数据"（`Find` + `Limit/Offset`）。
分页需要 total 才能告诉前端"还有没有下一页"。
如果只查一次、先 `Limit` 再 `Count`，total 可能永远等于 page_size —— 翻页就废了。

**A5** 查不到数据时：
- `var items []models.Item` → JSON 里是 `"list": null`
- `make([]models.Item, 0)` → JSON 里是 `"list": []`

前端的 `data.list.map(...)` 遇到 `null` 会直接崩溃报错。
所以**必须用 `make(..., 0)`**。

**A6** 都是**后端定的**。
`status` 强制为 `searching`（新帖一律从寻找中开始）；
`user_id` 取 token 里解出来的当前登录用户 ID。
如果让前端传 `user_id`，任何人都能冒充别人发帖 —— 这是安全底线。

**A7** 存了 `user_id`、`username`、`exp`（过期时间）、`iat`（签发时间），以及签名。
**不能立刻失效** —— JWT 是无状态的，服务端不留记录。
要"立刻失效"得引入 Redis 黑名单（把作废的 token 存起来，每次请求查一次），
这是本项目的取舍：为了简单，牺牲了"强制下线"的能力。

**A8** 返回 401 之后，**处理函数还会继续执行**。
比如"删除帖子"的接口，中间件发现没登录、返回了 401，
但代码继续跑到 `DeleteItem`，帖子真的被删了 ——
前端看到 401 以为没成功，实际上数据已经没了。**这是严重的安全漏洞。**

**A9** 因为中间件和 controller 是**两个独立的函数**，没有互相调用关系
（中间件是 Gin 调的，controller 也是 Gin 调的），没法直接传参数。
Context（`c`）是它们之间的"传递通道"，而且它**只属于这一次请求**，
不会串到别人的请求里去。

**A10** 因为状态机要求"只能前进不能回退"。
如果编辑接口能改 status，用户 `PUT` 一次就能把"已结束"改回"寻找中"，
`UpdateStatus` 里的校验就白写了。
所以状态变更必须走专门的 `PATCH /api/items/:id/status`。

</details>

# 第十一章 部署上线：从本地到服务器

## 11.1 先分清："本地能跑"和"别人能访问"是两回事

前面的章节里，你双击 `lostfound.exe`，浏览器打开 `http://localhost:8080`，一切正常。

但假设你把网址发给同学 —— **他打不开**。

原因在这一行：

```
localhost  =  "我这台电脑"
```

你访问 `localhost:8080`，找的是**你自己电脑**上的 8080 端口。
同学访问 `localhost:8080`，找的是**他自己电脑**的 8080 端口 —— 那里什么都没有。

| | 本地运行 | 线上部署 |
|---|---|---|
| 谁能访问 | 只有你自己 | 任何能上网的人 |
| 地址 | `localhost:8080` | `https://tsx.world/lostfound/` |
| 电脑关机后 | 服务消失 | 服务器 24 小时在线 |
| 用途 | 开发调试 | 作品展示、真实使用 |

"部署"要解决的就是：**把程序放到一台别人能通过网络找到的、永远开机的电脑上。**

## 11.2 部署后的完整架构

我们的部署长这样（每一个方框后面都会讲）：

```
                       https://tsx.world/lostfound/
                                  │
                                  ▼
                     ┌────────────────────────┐
                     │        Nginx           │  ← 门面：管 HTTPS、分路径
                     │  （服务器上的"总台"）     │
                     └───────┬────────┬───────┘
                             │        │
              /lostfound/    │        │   /lostfound/api/
              （静态页面）     │        │   （动态接口）
                             ▼        ▼
                   ┌──────────┐   ┌─────────────────┐
                   │ 前端文件   │   │   Go 服务        │ ← 真正干活的
                   │ web/*.html│   │ 127.0.0.1:8080  │   （systemd 托管）
                   └──────────┘   └────────┬────────┘
                                           │
                                           ▼
                                  ┌─────────────────┐
                                  │   MySQL 数据库   │
                                  │ 127.0.0.1:3306  │
                                  └─────────────────┘
```

注意两个 `127.0.0.1`：Go 服务和 MySQL **都只监听本机**，外网碰不到它们。
外界唯一的入口是 Nginx 的 443 端口 —— 这是安全设计，不是偶然。

## 11.3 第一步：交叉编译 —— 生成"Linux 认识"的程序

**问题**：你在 Windows 上编译出来的 `lostfound.exe`，是给 Windows 看的。
每个操作系统认识的可执行文件格式不同：

| 系统 | 可执行文件格式 | 长什么样 |
|---|---|---|
| Windows | PE | `lostfound.exe` |
| Linux | ELF | `lostfound`（没有 .exe 后缀） |

把 exe 直接传到 Linux 服务器上，它读不懂 —— 就像给只懂中文的人递一份英文合同。

**解法**：Go 语言自带**交叉编译** —— 在 Windows 上，直接编译出 Linux 能跑的程序：

```bash
# 在项目根目录执行（Git Bash / PowerShell 都可以）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o dist/lostfound_linux_amd64 .
```

三个环境变量，逐个解释：

| 变量 | 值 | 意思 |
|---|---|---|
| `GOOS` | `linux` | 目标操作系统：我要生成 **Linux** 的程序 |
| `GOARCH` | `amd64` | 目标 CPU 架构：64 位 x86 |
| `CGO_ENABLED` | `0` | 不依赖 C 语言库 → 编译出"纯静态"程序 |

`CGO_ENABLED=0` 值得多说一句：Go 默认可能调用系统里的 C 库，
关掉之后产出的程序**自带所有依赖**，扔到任何 Linux 上都能跑，不挑环境。

产物约 34MB —— 看起来大，但里面打包了 Go 运行时 + 所有依赖库（Gin、GORM 等），
**不需要在服务器上装 Go**，也不需要 `go mod download`。

> 一句话总结：这一步产出的是"能在 Linux 上运行的 exe"。

## 11.4 第二步：服务器准备 —— 装数据库、建库、建账号

服务器是一台全新的 Linux（我们的是一台阿里云轻量，Ubuntu 22.04），
上面什么都没有 —— 数据库要先装。

### 装 MySQL

```bash
sudo apt update
sudo apt install -y mysql-server
```

### 小内存机器的调优（重要）

我们的服务器只有 2G 内存，MySQL 默认配置比较"贪"，要让它省着点用：

```ini
# 写入 /etc/mysql/mysql.conf.d/zz-tune.cnf
[mysqld]
innodb_buffer_pool_size = 128M   # 缓存上限：从默认值调小
performance_schema = OFF         # 关掉性能监控表（小站用不上，省内存）
max_connections = 50             # 最大连接数：小站用不了那么多
innodb_log_file_size = 48M
```

改完重启：`sudo systemctl restart mysql`

### 建库 + 建专用账号

```sql
CREATE DATABASE lostfound CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 专用账号：只对这个库有权限，不用 root
CREATE USER 'lostfound'@'localhost' IDENTIFIED BY '你的强密码';
GRANT ALL PRIVILEGES ON lostfound.* TO 'lostfound'@'localhost';
FLUSH PRIVILEGES;
```

**为什么不用 root？** 和"不给客人家里所有房间的钥匙"一个道理：
万一这个账号泄露，损失被限制在 `lostfound` 这一个库里。

> 注意：**不用手动建表**。程序启动时 `AutoMigrate` 会自动按模型建表 —— 见 `main.go` 第 34 行。

## 11.5 第三步：文件就位 + 让程序"常驻"

### 服务器上的目录结构

```
/opt/lostfound/
├── lostfound        ← 交叉编译出来的二进制（要 chmod +x 才能执行）
├── config.yaml      ← 线上配置（数据库密码和 JWT 密钥与本地不同！）
├── web/             ← 前端 6 个页面
└── scripts/         ← seed_data.sh 等运维脚本
```

⚠️ **`config.yaml` 不能提交到 git**（含密码），它在 `.gitignore` 里；
线上的那份是单独准备的，密码、JWT 密钥都和本地不同。

### 为什么不能"直接跑起来就行"

你可能会想：SSH 上去 `./lostfound &` 让它后台跑不就完了？三个问题：

1. **关掉 SSH 窗口，程序就死了** —— 终端挂断时会给程序发信号
2. **服务器重启后，程序不会自己起来**
3. **程序崩溃后，没人把它拉起来**

systemd 一次解决这三个问题。我们写的服务文件：

```ini
# /etc/systemd/system/lostfound.service
[Unit]
Description=LostFound Go backend
After=network.target mysql.service     # 等网络和 MySQL 就绪再启动

[Service]
Type=simple
User=www-data                          # 用低权限用户跑，不用 root
WorkingDirectory=/opt/lostfound        # 程序读 config.yaml 的相对路径基准
ExecStart=/opt/lostfound/lostfound
Restart=always                         # 崩溃自动重启 ← 第 3 个问题的答案
RestartSec=3

[Install]
WantedBy=multi-user.target             # 开机自启 ← 第 2 个问题的答案
```

启用：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now lostfound   # enable=开机自启，--now=立刻启动
```

## 11.6 第四步：Nginx —— 网站的"总台"

服务器上已经有一个 Nginx（tsx.world 主站在用）。我们的项目挂上去，靠**路径**区分：

```
https://tsx.world/            → 主站首页
https://tsx.world/pingpong/   → 乒乓世界
https://tsx.world/lostfound/  → 校园失物招领系统 ← 新加的
```

为什么需要 Nginx 这一层，而不是让 Go 直接对外？

| 职责 | 谁来做 | 为什么 |
|---|---|---|
| HTTPS 加密 | Nginx | 证书只配一处，所有项目共享 |
| 域名 / 路径分发 | Nginx | 一个 443 端口，按路径分给不同项目 |
| 静态文件（html/css/js） | Nginx | 专业选手，比 Go 处理快 |
| 业务逻辑（/api/） | Go 服务 | 只有它懂业务 |

配置片段（加在 443 的 server 块里）：

```nginx
# API 反代：/lostfound/api/xxx → 转发给本机 8080 的 Go 服务
location /lostfound/api/ {
    proxy_pass http://127.0.0.1:8080/api/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 前端静态文件：Nginx 直接从磁盘拿
location /lostfound/ {
    alias /opt/lostfound/web/;
    index index.html;
}
```

`proxy_pass` 就是"**转发**"：浏览器请求 `tsx.world/lostfound/api/items`，
Nginx 转手把它发给 `127.0.0.1:8080/api/items`，拿到结果再还给浏览器。
对浏览器来说，它自始至终只跟 `tsx.world` 说话 —— **不知道 Go 服务的存在**。

### 关键问题：前端怎么知道后端在哪？

部署后有个隐蔽的坑：前端页面里如果写死 `http://localhost:8080/api`，
在**访问者的浏览器**里，`localhost` 指的是**访问者自己的电脑** —— 直接连不上。

所以 `web/js/api.js` 里做了三场景判断：

```js
const API_BASE = (() => {
  // ① 线上：Nginx 把 /lostfound/api/ 反代给后端
  if (location.hostname === 'tsx.world' || location.hostname === 'www.tsx.world') {
    return '/lostfound/api';
  }
  // ② 本地由后端托管（localhost:8080/app/）：同源，用相对路径
  if (location.port === '8080') return '/api';
  // ③ 本地前端单独打开（file:// 或别的端口）：指向本机后端
  return 'http://localhost:8080/api';
})();
```

同一份代码，在本地和线上都能正确找到后端 —— 这就是"环境自适应"。

## 11.8 部署踩过的坑（真实记录）

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| **Nginx 备份文件放错地方** | `nginx -t` 报 duplicate default server | `sites-enabled/` 目录下的**所有文件**都会被加载 —— 备份文件要放到别的目录 |
| **Git Bash 传中文变 GBK** | 库里存成 `Կ�״�` 乱码 | MSYS2 把命令行参数按 CP936 转码；请求体走文件、URL 参数用百分号编码 |
| **空列表返回 null** | 前端 `.map()` 直接崩 | Go 里用 `make([]Item, 0)` 而不是 `var items []Item`，保证返回 `[]` |
| **swap = 0 的风险** | 装 MySQL 时可能 OOM | 加 1G swap 兜底（内存不够时把冷数据挪到硬盘） |

## 11.9 小结

部署 = 把"只有你能访问的程序"变成"所有人都能访问的服务"。三件事：

1. **编译成目标系统能跑的格式** —— 交叉编译（GOOS / GOARCH）
2. **放到服务器上常驻** —— systemd 托管（开机自启 + 崩溃重启）
3. **让流量能找到它** —— Nginx 反代（HTTPS + 路径分发）

做完这三步，你的项目就有了一个**任何人点开就能用的网址**。

| **JavaScript（JS）** | 网页的**行为**：用户操作时发生什么（点按钮→发请求） |
| **前后端分离** | 页面文件只写"空壳"，数据由 JS 请求回来再填进去 |
| **fetch** | 浏览器内置的"发 HTTP 请求"函数 |
| **localStorage** | 浏览器里的"本地小仓库"，关掉浏览器再打开数据还在（我们用它存 token） |
| **接口文档 / 契约** | 前后端约定的"菜单"，写清楚要传什么、返回什么 |
| **请求 / 响应** | 你问一句（请求），对方答一句（响应） |
| **HTTP** | 浏览器和服务器说话的"语言规范" |
| **GET / POST / PUT / PATCH / DELETE** | 五种"请求类型"：拿/建/整体改/局部改/删 |
| **状态码** | 响应的结果编号：200 成功、401 没登录、403 没权限、404 找不到 |
| **JSON** | 一种双方约定好的数据格式 |
| **接口 / API** | 一个"功能入口"，比如"发布帖子"是一个接口 |
| **路由** | URL 到处理函数的对照表 |
| **中间件** | 处理请求前先过的"关卡" |
| **token / JWT** | 登录后拿到的"通行证" |
| **鉴权 / 认证** | 确认"你是谁"（Authentication） |
| **授权** | 确认"你能不能干这事"（Authorization） |
| **ORM** | 让你用代码操作数据库、不用手写 SQL 的工具（我们用 GORM） |
| **SQL** | 跟数据库说话的语言 |
| **主键 / ID** | 每条记录的唯一编号 |
| **自增** | ID 自动递增（1、2、3……），不用自己填 |
| **哈希** | 一种"单向加密"，能算出结果但反推不回去 |
| **盐（salt）** | 加密时混进去的随机字符串，让同样的密码算出不同结果 |
| **DSN** | 数据库连接字符串（地址+账号+密码+参数拼成的一串） |
| **迁移 / AutoMigrate** | 让代码自动把数据库表结构建起来 |
| **分页** | 一次只取一部分数据（第几页、每页几条） |
| **LIMIT / OFFSET** | 分页的两个参数：取几条 / 跳过几条 |
| **N+1 问题** | 列表里每一条都单独查一次数据库，导致查询次数爆炸 |
| **闭包** | 能"记住"外部变量的函数 |
| **哨兵错误** | 预定义好的错误值，用来判断"是哪种错" |
